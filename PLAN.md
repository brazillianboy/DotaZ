# DotaZ: implementation plan

## Цель
Пошагово реализовать проверяемый MVP DotaZ: авторизация, ввод ID матча, отчёт OpenDota по 10 игрокам, осторожный анализ, приватная история в Supabase и локализация RU/EN.

## Порядок работы
**Задача ChatGPT → промпт для Cline → выполнение в VS Code → локальная проверка → commit → push.**

Правила:
1. Выполнять **строго по одной задаче** в порядке ниже. Следующую начинать только после проверки и фиксации предыдущей.
2. Перед задачей ChatGPT формирует для Cline конкретный промпт: файлы, ограничения, критерии приёмки, команды проверки. Ученик передаёт промпт в Cline, а не проектирует его самостоятельно.
3. Cline сначала изучает существующий код и не заменяет рабочие решения без причины. Не добавляет функциональность будущих задач.
4. После выполнения Cline сообщает изменённые файлы, результаты тестов и обнаруженные ограничения. Ученик лично проверяет сценарий в браузере и терминале.
5. При провале проверки исправить **в рамках текущей задачи**, повторить проверку; лишь затем выполнить `git add`, `git commit`, `git push`.
6. В Git не передавать `.env`, API-токены, ключи Supabase service_role, пароли, логи с секретами. Не использовать service_role в браузере.
7. Статус каждой задачи: `planned` → `in_progress` → `verified` → `done` (`blocked` — если не выполнена зависимость). `done` допустим только после успешного push.
8. После каждой завершённой задачи обновлять `PLAN.md`: статус, commit hash, что проверено. Само обновление включать в коммит задачи.
9. Технологический стек **сначала проверить в репозитории**; не считать React/Vite или конкретный backend уже выбранными, пока это не подтверждено.

## Готовность проекта
- Все обязательные задачи 1–13 имеют статус `done`.
- Проверены вход, загрузка тестового матча, 10 участников, повторный анализ, приватность истории и реакции на ошибки.
- Недоступные сведения не подменяются нулём; непроверенные оценки линии не отображаются.

- Пустой, текстовый, отрицательный ID, 404, 403, 429, 5xx, таймаут и сетевой сбой не приводят к падению страницы.

**Цель:** история надёжно хранится и изолирована по пользователям.

**Изменения:** подготовить миграцию с профилями и отчётами, связью с auth.users, `UNIQUE(user_id, match_id)`, timestamp, версией правил и содержимым отчёта; включить и проверить RLS. Ранее подготовленный SQL — только проектный шаблон: не запускать без сверки существующей схемы и миграций.

- Повторная запись пары `(user_id, match_id)` не создаёт дубликат; тестируются ошибки прав и пустые данные.

## Task 11: Сохранение и повторное использование отчёта
**Цель:** анализ автоматически попадает в личную историю и не дублируется.

**Зависимости:** Tasks 7, 9, 10.

**Изменения:** проверить наличие отчёта для текущего пользователя перед новым анализом; сохранять общие сведения и разделы всех игроков в одной записи; использовать безопасный upsert/обработку гонок с уникальным ограничением; явно определить повторное обновление по версии правил.

**Проверка:**
- Первый анализ сохраняется; повторный открывает тот же отчёт без лишней записи.
- Два почти одновременных запроса не создают двух строк; ошибка записи не маскируется как успешное сохранение.
