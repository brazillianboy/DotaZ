# DotaZ

## Обзор проекта

**DotaZ** — веб-сайт для анализа матчей Dota 2 по ID матча: пользователь вводит числовой ID матча и получает достоверную статистику, наблюдения с указанием источника данных и личную историю отчётов. Принцип продукта: не выдавать гипотезы за доказанные игровые ошибки.

Источники требований: `Product_brief.md` (продуктовый бриф), `ARCHITECTURE.md` (техническая спецификация MVP), `PLAN.md` (план реализации, Tasks 1–13), `AUDIT_REPORT.md` (отчёт аудита документации от 14.10.2026).

> **Текущее состояние (14.10.2026): реализован каркас фронтенда (Task 2) и аутентификация через Supabase Auth (Task 3).**
> Приложение — SPA на React + TypeScript + Vite с маршрутизацией, дизайн-системой
> по визуальному референсу и рабочими формами регистрации/входа. Анализ матчей,
> данные и история **ещё не реализованы**: элементы анализа помечены как дизайн-превью.
>
> **Важно:** живая проверка регистрации, входа, сессии и выхода с реальным проектом
> Supabase на момент обновления документации **не выполнялась** — на локальной машине
> отсутствует конфигурация `.env`. Наличие кода не означает, что сценарии проверены вживую.

### Что уже реализовано

- Каркас SPA: React 18 + TypeScript + Vite + React Router, чистый CSS.
- Глобальная шапка: бренд «DotaZ», навигация, переключатель языка (превью), состояние
  аутентификации (кнопки «Войти»/«Зарегистрироваться» либо индикатор аккаунта и «Выйти»).
- Главная страница по референсу: hero с формой-превью ID матча, карточка-превью матча, ряд возможностей, секция «Как это работает?», четыре карточки-раздела.
- Аутентификация через Supabase Auth (Task 3): регистрация, вход, выход, восстановление
  сессии после перезагрузки, обработка подтверждения email — см. раздел
  «Аутентификация (Supabase Auth)».
- Защита приватного маршрута `/history` (Task 4): доступ только после подтверждения
  сессии, редирект неавторизованных на `/login`, возврат на исходный маршрут после входа —
  см. раздел «Защищённые маршруты (Task 4)».
- Ввод ID матча и получение матча из OpenDota (Task 5): валидация ID на главной и на
  странице матча, запрос `GET /api/matches/{match_id}` с таймаутом и отменой,
  состояния загрузки/ошибок/успеха — см. раздел «Получение матча из OpenDota (Task 5)».
- Нормализация данных матча (Task 6): единая типобезопасная модель матча и участников,
  различение отсутствующих значений (`null`) и легитимного нуля, определение сторон
  по `player_slot`, модульные тесты — см. раздел «Нормализация данных матча (Task 6)».
- Страница матча с выбором игрока (Task 7): сводка матча, группировка участников
  по Radiant/Dire, выбор участника и его фактические K/D/A, GPM, XPM, last hits —
  см. раздел «Страница матча и выбор игрока (Task 7)».
- Фактический отчёт о стадии линии 00:00–15:00 (Task 8): поминутные показатели
  (`lh_t[15]`, `gold_t[15]`, `xp_t[15]`), события и покупки первых пятнадцати минут,
  процент эффективности линии OpenDota — см. раздел «Ранняя стадия 00:00–15:00 (Task 8)».
- Движок наблюдений и рекомендаций v1 (Task 9): детерминированные фактологические
  наблюдения с подтверждениями (поле + значение), версия правил, честные ограничения —
  см. раздел «Наблюдения и рекомендации (Task 9)».
- Схема Supabase и RLS (Task 10): миграция для `profiles` и `match_reports`
  (владение через RLS, идемпотентный backfill профилей, триггер регистрации) **применена
  владельцем**; read-only аудит, план проверки и временный скрипт живой проверки —
  см. раздел «Схема Supabase и RLS (Task 10)». Анонимный доступ проверен и закрыт;
  проверка двумя пользовательскими сессиями ожидает запуска владельцем (`NOT RUN`).
- Личные отчёты (Task 11): анализ автоматически сохраняется в `public.match_reports`
  (весь матч и разбор всех участников), повторное открытие использует сохранённый снимок
  без запроса к OpenDota и без пересчёта правил, дубликаты исключены ограничением
  `UNIQUE (user_id, match_id)` — см. раздел «Личные отчёты (Task 11)».
- Личная история анализов (Task 12): приватная страница `/history` со списком своих
  сохранённых отчётов (ID матча, дата, результат, статус), сортировкой по дате и
  переходом к сохранённому отчёту — см. раздел «Личная история (Task 12)».
- Маршруты: `/`, `/login`, `/register`, `/auth/confirm`, `/heroes`, `/matches/:matchId`, `/history` и страница 404 для неизвестных адресов.
- Адаптивная вёрстка (десктоп/планшет/мобильные), доступная навигация с клавиатуры.

## Конфигурация окружения

Приложению требуются две переменные окружения для клиента Supabase Auth:

```env
VITE_SUPABASE_URL=
VITE_SUPABASE_PUBLISHABLE_KEY=
```

| Переменная | Назначение | Где взять в Supabase Dashboard |
|---|---|---|
| `VITE_SUPABASE_URL` | URL проекта Supabase | **Project Settings → Data API** (Project URL) |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публичный publishable (или legacy anon) ключ | **Project Settings → API Keys** |

Порядок локальной настройки:

1. Скопируйте `.env.example` в `.env` в корне проекта.
2. Подставьте значения своего проекта Supabase (см. таблицу выше).
3. Перезапустите dev-сервер: Vite читает `.env` при старте, поэтому после изменения файла
   сервер нужно остановить и запустить заново.
4. Никогда не коммитьте `.env` — он исключён из Git через `.gitignore`
   (также исключены `node_modules/`, `dist/`, `*.log`).

**Допускаются только публичные browser-safe ключи.** Vite подставляет значения всех
переменных с префиксом `VITE_` прямо в клиентский бандл, поэтому они видны любому
пользователю в браузере. Запрещено использовать:

- `service_role`-ключ Supabase;
- секретные ключи вида `sb_secret_...`;
- пароли базы данных;
- приватные API-токены и любые административные учётные данные.

Эти значения нельзя добавлять ни в `.env`, ни в клиентский код. Внешние запросы,
требующие секретов, выполняются на доверенном сервере или в Edge Function
(`PLAN.md`, правило 6; `ARCHITECTURE.md`, п. 7).

Если переменные не заданы, приложение не падает: страницы входа и регистрации
показывают сообщение «Авторизация недоступна: Supabase не настроен», а остальные
разделы работают в режиме дизайн-превью.

## Аутентификация (Supabase Auth)

Аутентификация реализована в Task 3 на официальном клиенте `@supabase/supabase-js`
(источник истины — Supabase Auth; собственных токенов и хранилищ сессий нет).

### Реализованные возможности

| Возможность | Реализация |
|---|---|
| Регистрация по email и паролю | `/register`, `supabase.auth.signUp()` |
| Вход по email и паролю | `/login`, `supabase.auth.signInWithPassword()` |
| Выход | кнопка «Выйти» в шапке, `supabase.auth.signOut()` |
| Необязательное подтверждение email | поддержаны оба режима Supabase: с подтверждением и без него |
| Обработка перехода по ссылке подтверждения | маршрут `/auth/confirm` |
| Восстановление сессии после перезагрузки | `getSession()` + подписка `onAuthStateChange()` |
| Обработка ошибок аутентификации | понятные русские сообщения без технических деталей |
| Состояние аутентификации в шапке | кнопки «Войти»/«Зарегистрироваться» или email аккаунта и «Выйти» |

Реализация: `src/lib/supabase.ts` (единственный экземпляр клиента), `src/lib/authErrors.ts`
(перевод ошибок), `src/contexts/AuthContext.tsx` (состояние и операции),
`src/hooks/useAuth.ts` (доступ из компонентов), `src/pages/LoginPage.tsx`,
`src/pages/RegisterPage.tsx`, `src/pages/AuthConfirmPage.tsx`, `src/components/AppHeader.tsx`.

### Регистрация

1. Откройте `/register` (кнопка «Зарегистрироваться» в шапке).
2. Укажите email и пароль, затем повторите пароль (значения должны совпадать).
3. Нажмите «Зарегистрироваться». Пока запрос выполняется, кнопка блокируется
   от повторной отправки.
4. Следуйте инструкциям на экране:
   - **подтверждение email включено** — показывается нейтральное сообщение
     **«Проверьте электронную почту»**: «Если регистрация доступна для этого адреса,
     вы получите письмо с дальнейшими инструкциями. Если у вас уже есть аккаунт,
     попробуйте войти.» После подтверждения адреса выполните вход на `/login`;
   - **подтверждение email отключено** — приложение сразу сообщает
     «Аккаунт создан — вы вошли в систему.»

Приложение **не раскрывает**, зарегистрирован ли произвольный адрес: сообщение не
утверждает, что аккаунт точно создан, а письмо точно отправлено; поиск дубликатов
и запросы к административным API Supabase не выполняются.

### Вход и выход

- **Вход** — `/login` (кнопка «Войти» в шапке): email и пароль, маскировка пароля,
  отправка по Enter, состояние загрузки, защита от повторных отправок. После успешного
  входа пользователь возвращается на главную страницу.
- **Ошибки входа** показываются короткими русскими сообщениями: неверный email или
  пароль; email не подтверждён; сеть недоступна; превышен лимит попыток; проблемы
  конфигурации. Технические детали и токены не выводятся.
- **Состояние в шапке**: пока сессия проверяется — «Проверка…»; при активной сессии —
  email аккаунта и кнопка «Выйти»; иначе — кнопки «Войти»/«Зарегистрироваться».
- **Выход** — кнопка «Выйти» в шапке; состояние обновляется сразу, пользователь
  возвращается на главную, перезагрузка страницы не восстанавливает сессию.
- **Сессия** сохраняется официальным клиентом Supabase и восстанавливается после
  перезагрузки страницы (стандартные `persistSession` / `autoRefreshToken`).
- Защищённые маршруты **реализованы** (Task 4): `/history` доступен только после
  подтверждения сессии, иначе — редирект на `/login` с возвратом на исходный адрес.
  Содержимое раздела — личная история анализов (Task 12).

### Подтверждение email (`/auth/confirm`)

Маршрут `/auth/confirm` обрабатывает переход по ссылке из письма Supabase. По
фактическому коду `src/pages/AuthConfirmPage.tsx` поддерживаются стандартные варианты:

1. `?code=...` (PKCE) → `exchangeCodeForSession()`;
2. `?token_hash=...&type=...` → `verifyOtp()`;
3. implicit-переход с токенами в hash адреса — обрабатывается официальным клиентом
   (`detectSessionInUrl`).

Возможные исходы:

- **успех** — «Email подтверждён — аккаунт активирован. Теперь вы можете войти.»
  с кнопкой «Перейти ко входу»;
- **недействительная или устаревшая ссылка** — понятное сообщение с предложением
  запросить новое письмо;
- **конфигурация Supabase отсутствует** — сообщение «Подтверждение недоступно:
  Supabase не настроен…».

### Что проверено, а что нет

- **Проверено:** сборка проекта без ошибок TypeScript; рендеринг страниц `/login`,
  `/register`, `/auth/confirm`; корректное сообщение при отсутствии конфигурации Supabase;
  сохранение прежнего дизайна и маршрутов.
- **Не проверено вживую (NOT RUN):** фактическая регистрация, вход с реальными
  учётными данными, восстановление сессии после перезагрузки, выход и переход по ссылке
  подтверждения — для этого нужен настроенный проект Supabase и тестовые аккаунты.
  Сценарии считаются **не подтверждёнными**, пока владелец проекта не выполнит проверку.
  Это относится и к сценариям Task 4, требующим реального входа (доступ к `/history`
  авторизованным пользователем, возврат после входа, сохранение сессии, выход).

## Защищённые маршруты (Task 4)

Приватным является маршрут `/history` — раздел личной истории. Он обёрнут в компонент
`src/components/ProtectedRoute.tsx`, который использует существующий контекст
аутентификации (`useAuth`); второй клиент Supabase и отдельное хранилище сессии не создаются.

### Поведение

| Состояние | Поведение |
|---|---|
| Идёт инициализация аутентификации (`loading`) | Показывается статус «Проверка авторизации…»; приватный контент не рендерится и редирект не выполняется (чтобы не выкинуть авторизованного пользователя при обновлении страницы) |
| Сессия подтверждена | Рендерится страница `/history` |
| Пользователь не авторизован | Редирект на `/login` с сохранением исходного внутреннего маршрута в навигационном state |
| Сессия не подтверждена (ошибка инициализации, отсутствие конфигурации Supabase, истёкшая/недействительная сессия) | Fail closed: приватный контент не показывается, пользователь отправляется на `/login`, где видит понятное состояние |

### Возврат на исходный маршрут

1. Неавторизованный пользователь открывает `/history`.
2. `ProtectedRoute` перенаправляет его на `/login` и передаёт исходный путь через state.
3. После успешного входа приложение возвращает пользователя на этот путь.

Принимаются **только внутренние** пути приложения: внешние адреса, protocol-relative
(`//example.com`), пути с обратными слэшами и сам `/login` отклоняются — в таких случаях
используется `/` (защита от open redirect). Если пользователь открыл `/login` напрямую
(без предварительного запроса приватной страницы), после входа выполняется переход на `/`.
Информация о возврате хранится только в навигационном state React Router и не
записывается в browser storage.

### Реакция на изменение состояния

- **Выход:** состояние аутентификации обновляется через Supabase Auth, приватный контент
  перестаёт рендериться, пользователь на `/history` перенаправляется на `/login`.
- **Истечение/недействительность сессии:** обновление состояния выполняет официальный
  клиент Supabase (`onAuthStateChange`, автообновление токенов); защищённый контент
  не показывается по устаревшему состоянию.
- **Временные сетевые сбои** не приводят к уничтожению ранее восстановленной сессии
  произвольным образом: клиент Supabase сам решает, обновлять или завершать сессию.
- **Отсутствие конфигурации Supabase** не даёт циклов редиректов: `/login` — публичная
  страница и показывает сообщение «Авторизация недоступна: Supabase не настроен».

### Ограничение защиты

Защита маршрутов реализована **только на стороне клиента** и является механизмом
управления интерфейсом. Она **не заменяет** серверную авторизацию и политики Supabase
Row Level Security: ограничение доступа к данным в базе — задача Task 10. Прямых запросов
к базе данных в Task 4 нет, история остаётся заглушкой.

## Получение матча из OpenDota (Task 5)

Ввод ID матча на главной странице и страница `/matches/:matchId` получают реальные данные
из OpenDota.

### Архитектура запросов

- Endpoint: `GET https://api.opendota.com/api/matches/{match_id}`.
- Слой доступа: `src/lib/opendota.ts` — минимальный публичный клиент на нативном `fetch`
  (Axios и другие HTTP-зависимости не добавлялись).
- Запрос выполняется **напрямую из браузера**: endpoint публичный, ключ не требуется,
  провайдер поддерживает браузерный доступ (ответ содержит `Access-Control-Allow-Origin`
  с эхо-значением Origin — проверено). Прокси и серверный слой в Task 5 не нужны.
- Секретные ключи OpenDota в браузер не помещаются: запросы с секретами должны выполняться
  на доверенном сервере или в Edge Function (`ARCHITECTURE.md`, п. 7).

### Таймаут, отмена и устаревшие ответы

- Таймаут запроса — **15 секунд** (`OPENDOTA_REQUEST_TIMEOUT_MS`); по истечении
  показывается сообщение об истечении времени ожидания с возможностью повтора.
- Запрос отменяется через `AbortController` при уходе со страницы матча, смене маршрута
  и перед новым запросом; таймер очищается.
- Отменённые и устаревшие ответы не применяются к интерфейсу (проверяется `signal.aborted`).
- Отмена (уход со страницы) отличается от таймаута: это разные сообщения.

### Валидация ID матча

Принимается только положительное целое число: только цифры, без пробелов внутри, знаков,
точки, экспоненты и букв; ведущие и замыкающие пробелы обрезаются. Отклоняются пустой ввод,
ноль, отрицательные и дробные значения, научная нотация и слишком длинные значения
(более 19 цифр). ID хранится строкой — числовые преобразования с потерей точности не
выполняются. При неверном ID запрос к OpenDota **не отправляется**: сообщение показывается
рядом с полем на главной или на странице матча (при прямом URL).

### Поведение на главной и на странице матча

1. Пользователь вводит ID на главной (`/`) и отправляет форму (Enter или кнопка
   «Анализировать»).
2. ID валидируется; при успехе выполняется переход на `/matches/{id}`.
3. Страница матча валидирует параметр маршрута повторно (не полагаясь только на главную)
   и выполняет запрос к OpenDota, показывая состояние загрузки.
4. Прямое открытие `/matches/{id}`, обновление страницы и переходы Back/Forward работают так же.

### Состояния и обработка ошибок

| Ситуация | Сообщение и поведение |
|---|---|
| Загрузка | «Запрашиваем данные матча у OpenDota…» |
| HTTP 200 | Подтверждение получения данных и только поля, фактически присутствующие в ответе (ID матча, длительность, победитель, количество участников) |
| HTTP 404 | «Матч не найден. Проверьте ID и попробуйте снова.» |
| HTTP 401/403 | Сообщение об ограничении доступа к провайдеру (не «матч не найден») |
| HTTP 429 | «Превышен лимит запросов OpenDota. Попробуйте позже.» |
| HTTP 5xx | Сообщение о временной недоступности сервиса OpenDota |
| Таймаут | Сообщение об истечении времени ожидания (15 секунд) и кнопка «Повторить запрос» |
| Сетевой сбой | Сообщение о недоступности сети или провайдера |
| Некорректный ответ | Сообщение об ошибке обработки ответа OpenDota |
| Некорректный ID | Сообщение валидации; запрос к OpenDota не отправляется |

Для временных сбоев (таймаут, сеть, 429, 5xx) доступна кнопка ручного повтора.
Автоматических повторных запросов нет.

### Тестовый матч

Проверочный ID из документации — `9007760151`. На нём подтверждён успешный ответ OpenDota
(HTTP 200) и корректный разбор JSON.

### Что относится к следующим задачам

Task 5 **не** выполняет нормализацию полного ответа, расчёты (KDA, GPM, XPM), разбор линии
первых минут, наблюдения, рекомендации и сохранение отчётов — это Tasks 6–12. Отсутствующие
поля не заменяются нулями, а количество участников не предполагается равным десяти.

## Нормализация данных матча (Task 6)

Ответ OpenDota — недоверенный внешний ввод. Между API и UI добавлен единый слой
нормализации: `src/lib/normalizeMatch.ts` (чистая функция `normalizeMatch(raw: unknown)`)
и типы `src/types/match.ts`.

Слой не зависит от React (нет хуков, состояния, HTTP и обращений к Supabase),
не изменяет входной объект и детерминирован: одинаковый вход даёт одинаковый результат.

### Нормализованная модель

`NormalizedMatch`:

| Поле | Тип | Правило |
|---|---|---|
| `match_id` | `string \| null` | Десятичная строка без потери точности; недоступное или небезопасное число → `null` (никогда не `"0"`) |
| `duration` | `number \| null` | Секунды; легитимный `0` сохраняется; отсутствие/некорректность → `null` |
| `radiant_win` | `boolean \| null` | Только `true`/`false`; отсутствие → `null` (никогда не `false`) |
| `players` | `NormalizedPlayer[]` | Только фактически присутствующие и идентифицируемые записи; массив может быть пустым |

`NormalizedPlayer`: `player_slot: number`, `team: 'radiant' | 'dire' | null`,
`hero_id`, `kills`, `deaths`, `assists`, `gold_per_min`, `xp_per_min`, `last_hits` —
все числовые поля `number | null`.

### Правила значений

- **Отсутствующие данные ≠ ноль.** Отсутствующее, `null` или некорректное значение
  становится `null`; легитимный `0` сохраняется как `0`.
- **Никаких приведений типов.** Строки (`'2069'`), булевы значения и дробные числа
  не превращаются в статистику; строгая проверка `typeof value === 'number'` и
  `Number.isInteger` (для целочисленных полей).
- **Отсутствие данных не трактуется как плохой результат игрока** — оценок в слое нет.

### Определение сторон

Сторона определяется только по `player_slot` (конвенция OpenDota):
`0–127` → `radiant`, `128–255` → `dire`. Порядок записей в массиве и победитель матча
для определения стороны **не используются**; слот `0` — валидный Radiant, `128` — валидный Dire.
Записи без целочисленного `player_slot` исключаются из нормализованного массива
(модель идентифицирует участников по слоту, выдумывать слот нельзя);
записи с целым слотом вне диапазона сохраняются, но `team` = `null`.

### Частичные ответы API

Нормализация не падает и не фабрикует данные при:

- отсутствии `duration`, `radiant_win` или `match_id`;
- отсутствующем или некорректном массиве `players` (результат — пустой массив);
- меньшем числе участников (синтетические записи до десяти **не создаются**);
- отсутствующих статистиках у части игроков (`null`, а не `0`);
- неверных типах полей, `NaN`, `Infinity`, отрицательной длительности;
- ответе, не являющемся объектом (`null`, строка, массив → пустая модель).

### Модульные тесты

Тесты нормализации: `src/lib/normalizeMatch.test.ts` (Vitest, 14 категорий, 48 проверок):

```powershell
npm.cmd test        # vitest run (неинтерактивный запуск)
```

Покрытие: полный валидный матч; стороны Radiant (0/1/127) и Dire (128/129/255);
некорректные слоты; легитимные нули; отсутствующие и явные `null`-статистики;
отсутствующий/некорректный массив игроков; неполный список участников (без фабрикации
до десяти); неверные типы полей; иммутабельность входа; детерминизм; большие ID
(без потери точности); реальная фикстура `samples/match-.json` (файл не изменялся).

### Интеграция со страницей матча

`src/pages/MatchPage.tsx` применяет нормализацию сразу после успешного получения данных
и отображает только нормализованные поля: запрошенный ID, `match_id` из ответа
(или «нет данных в ответе»), длительность, победителя, количество участников и стороны
по `player_slot`. Состояния загрузки/ошибок, кнопка повтора и ссылки сохранены.
Ошибки HTTP-клиента (Task 5) не нормализуются как валидный матч.

### Что относится к следующим задачам

Слой нормализации **не** выполняет аналитику: нет расчётов KDA/GPM/XPM, сравнений,
разбора линии, оценок качества игры и рекомендаций. Панель статистики десяти игроков,
выбор игрока и отчёты — Tasks 7+. Данные матча не сохраняются (ни Supabase, ни локально).

## Страница матча и выбор игрока (Task 7)

Маршрут `/matches/:matchId` превращён из подтверждения получения данных в интерактивную
страницу разбора матча. Источник данных — нормализованная модель Task 6
(`normalizeMatch`); страница не читает «сырые» поля OpenDota напрямую.

### Компоненты

| Компонент | Ответственность |
|---|---|
| `src/pages/MatchPage.tsx` | Запрос через существующий клиент OpenDota, нормализация, состояния загрузки/ошибок, локальное состояние выбранного игрока, композиция интерфейса |
| `src/components/MatchSummary.tsx` | Сводка матча: ID, длительность, победитель, число участников, источник данных |
| `src/components/PlayerSelector.tsx` | Список участников по сторонам и выбор игрока |
| `src/components/PlayerStats.tsx` | Фактическая статистика выбранного игрока |

### Сводка матча

- **ID матча** — запрошенный в заголовке и значение из ответа (`match_id`).
- **Длительность** — `MM:SS` и исходное значение в секундах.
- **Победитель** — по `radiant_win`: `true` → Radiant, `false` → Dire, `null` → «Нет данных» (отсутствие результата **не** трактуется как победа Dire).
- **Участников в ответе** — фактическое количество; при отсутствии данных — «Нет данных».
- **Источник данных** — OpenDota.

Если участников меньше десяти, показывается фактическое число: синтетические записи
не создаются.

### Выбор игрока

- Участники группируются по стороне из `player_slot` (Radiant / Dire); записи с
  неопределённой стороной попадают в группу **«Команда не определена»** и не приписываются
  к Radiant или Dire. Порядок массива для группировки не используется.
- Подпись участника — фактический идентификатор: «Игрок — слот N»; при наличии
  подтверждённого `hero_id` добавляется «· герой N» (справочник героев не реализован,
  ники не выдумываются).
- **По умолчанию** выбирается первый доступный участник; при отсутствии участников
  ничего не выбрано.
- Выбор — обычные кнопки: работают мышью и клавиатурой (Tab + Enter/Space),
  состояние передаётся через `aria-pressed`, выбранный элемент дополнительно помечен
  текстом «Выбран» и красной подсветкой (не только цветом).
- Переключение игрока обновляет панель статистики **без новых запросов** к OpenDota.
- При смене маршрута на другой матч выбор сбрасывается, прежние данные не показываются,
  незавершённый запрос отменяется (`AbortController`), устаревшие ответы не применяются.

### Статистика выбранного игрока

Отображаются только нормализованные факты: слот, сторона, `hero_id`, K / D / A, GPM,
XPM, last hits.

- **K/D/A** — сырые значения в формате `kills / deaths / assists` (например, `6 / 8 / 18`).
  Коэффициент KDA **не рассчитывается**: документацией не задана единая формула, поэтому
  показываются исходные значения.
- **GPM и XPM** — как есть из ответа; без сравнения с нормативами героя и роли и без оценок
  «хорошо/плохо».
- **Last hits** — показатель за матч; он **не** трактуется как добивания за первые 10 минут.
- **Отсутствующие значения** — «Нет данных» (в K/D/A — прочерк «—» для конкретной части);
  легитимный ноль показывается как `0` и никогда не подменяется на «Нет данных».

Если в ответе нет ни одного валидного участника, выводится сообщение
«Данные об участниках отсутствуют.», при этом сводка матча показывается, если
фактические данные матча доступны.

### Состояния и ошибки

Состояния Task 5 сохранены без изменений: загрузка, успех, некорректный ID, «матч не найден»,
превышен лимит запросов, ошибка доступа провайдера, ошибка сервера провайдера, сеть,
таймаут, некорректный ответ — с кнопкой повтора для временных сбоев. Отмена запроса и

## Ранняя стадия 00:00–15:00 (Task 8)

Отчёт о первых пятнадцати минутах матча для выбранного участника. Используются только
подтверждённые поля ответа OpenDota; при их отсутствии показывается ограничение,
а не выдуманные значения.

### Проверенные поля OpenDota (живой ответ для матча `9007760151`)

| Поле | Наличие | Фактический тип и семантика |
|---|---|---|
| `lh_t` | у всех 10 участников | массив накопительных значений; длина 35 = ⌊duration/60⌋ + 1; индекс 0 → 0:00, **индекс 15 → 10:00** |
| `gold_t` | у всех 10 участников | массив накопительного золота, та же индексация |
| `xp_t` | у всех 10 участников | массив накопительного опыта, та же индексация |
| `kills_log` | у всех | массив событий `{ time: <секунды>, key: <npc…> }` |
| `deaths_log` | у всех | массив событий той же структуры |
| `purchase_log` | у всех | массив `{ time: <секунды>, key: <предмет> }`; **встречаются отрицательные времена** (предматчевая закупка, например `time = −89`) |
| `lane_efficiency_pct` | у всех | число в шкале 0–100 (подтверждено парным полем `lane_efficiency` = 0.78 при `lane_efficiency_pct` = 78) |

Ограничения исследования: наличие расширенных полей зависит от обработки реплея
OpenDota. Для других матчей они могут отсутствовать — приложение обязано работать
без них. Если массив короче 11 элементов, значение 10-й минуты считается недоступным
(экстраполяция не выполняется).

### Правила разбора

- **Интервал отчёта:** 00:00–15:00; для событий — `time` в секундах от 0 до 900
  включительно. Предматчевые записи (`time < 0`) и события после 10:00 в отчёт не входят.
- **Таймлайны:** строгая проверка массива и значения; `0` сохраняется как `0`;
  отсутствующее, нечисловое, `NaN`/`Infinity` или слишком короткий массив → `null`.
- **События:** журнал отсутствует или содержит запись с невалидным временем → `null`
  («данных нет»), чтобы не выдавать недостоверный итог. Пустой журнал → `0`
  (событий в интервале не было).
- **Покупки:** `null` — журнал недоступен; `[]` — журнал получен, но покупок в интервале
  нет. Ключи предметов выводятся как есть, без справочника названий.
- **Эффективность линии:** показывается только значение OpenDota в шкале 0–100;
  вне диапазона или не-число → `null`. Значение не переводится в оценку качества.
- `last_hits` за весь матч **не** подменяет `lh_t[15]`; GPM/XPM за матч **не**
  пересчитываются в поминутные показатели.

## Наблюдения и рекомендации (Task 9)

Движок правил `src/lib/analysisRules.ts` формирует для выбранного участника
детерминированные **фактологические наблюдения** на основе уже загруженных
нормализованных данных (Tasks 6–8). Оценки качества игры, сравнения с нормативами
и советы по игре не формируются.

### Версия правил

`ANALYSIS_RULES_VERSION = '1.0.0'` — единая константа; версия записывается в каждое
наблюдение и в результат анализа. Изменение поведения правил требует новой версии,
чтобы смысл ранее сохранённых отчётов не менялся молча.

### Структура наблюдения

```ts
interface AnalysisObservation {
  rule_id: string            // стабильный идентификатор правила
  rule_version: string       // версия правил (1.0.0)
  player_slot: number        // участник, к которому относится наблюдение
  metric: string             // машинное имя показателя
  period: string             // «весь матч» или «00:00–15:00»
  source: 'OpenDota'
  text: string               // текст наблюдения на русском
  evidence: { field, value, period, source }[]
  limitations: string[]
}
```

Все структуры JSON-сериализуемы и не содержат React-элементов.

### Реализованные правила (v1.0.0)

| `rule_id` | Входные метрики | Подтверждения (`field`) | Период | Пример текста |
|---|---|---|---|---|
| `match.kda` | `kills`, `deaths`, `assists` | `kills`, `deaths`, `assists` | весь матч | «Итог матча: убийства — 16, смерти — 3, ассисты — 15.» |
| `laning.last_hits_at_10` | `laning.lastHitsAt10` (`lh_t[15]`) | `lh_t[15]` | 00:00–15:00 | «Добивания к 15:00 (lh_t[15]) — 47.» |
| `laning.kills_deaths_first_10` | `killsFirst10`, `deathsFirst10` | `kills_log (00:00–15:00)`, `deaths_log (00:00–15:00)` | 00:00–15:00 | «Первые десять минут: убийства — 3, смерти — 1.» |
| `laning.gold_at_10` | `goldAt10` (`gold_t[15]`) | `gold_t[15]` | 00:00–15:00 | «Накопленное золото к 15:00 (gold_t[15]) — 3864.» |
| `laning.xp_at_10` | `xpAt10` (`xp_t[15]`) | `xp_t[15]` | 00:00–15:00 | «Накопленный опыт к 15:00 (xp_t[15]) — 2907.» |
| `laning.purchases_first_10` | `purchasesFirst10` | `purchase_log (00:00–15:00)` | 00:00–15:00 | «Покупки в интервале 00:00–15:00: 10.» |
| `laning.efficiency_pct` | `laneEfficiencyPct` | `lane_efficiency_pct` | 00:00–15:00 | «Эффективность линии по данным OpenDota (lane_efficiency_pct) — 78 % (значение провайдера, не пересчитано DotaZ).» |

Правила выполняются в фиксированном порядке; наблюдения не дублируют друг друга
и не перефразируют одни и те же подтверждения. Если правило не может быть выполнено
(нет данных), оно **не** создаёт наблюдение, а добавляет соответствующее ограничение.

### Политика рекомендаций

В версии правил **1.0.0 список рекомендаций всегда пуст**: в документации проекта
(`ARCHITECTURE.md`, п. 6.3) не подтверждены нормы героя и роли, поэтому объективных
условий для советов нет. Вместо выдуманных рекомендаций интерфейс показывает честное
пояснение:

> Объективные рекомендации недоступны: в документации проекта не подтверждены нормы
> героя и роли, поэтому сравнение показателей с эталоном и советы по игре не формируются.
> Наблюдения выше описывают только факты из ответа OpenDota.

Пустой список рекомендаций — ожидаемое состояние, а не ошибка реализации. Запрещённые
формулировки (оценки «хорошо/плохо», пороги «минимум N добиваний», «предмет куплен поздно»,
«слишком много смертей») не используются: это проверяется юнит-тестами.

### Ограничения и неполные данные

- `null` означает отсутствие данных и никогда не подменяется нулём; легитимный `0`
  (например, 0 убийств или пустой журнал покупок) сохраняется как факт.
- Отсутствующее поле влияет только на своё правило: остальные наблюдения формируются.
- Ограничения выдаются точечно: нет `lh_t` — ограничение по добиваниям к 15:00; нет
  журналов событий — ограничение по событиям; нет журнала покупок — ограничение по покупкам;
  нет `lane_efficiency_pct` — ограничение по эффективности.
- Всегда добавляется принципиальное ограничение `benchmarks.hero_role_missing`:
  нормы героя и роли не подтверждены, поэтому сравнение и оценка качества не выполняются.
- Если подтверждённых наблюдений нет вовсе, показывается «Недостаточно данных для достоверной оценки.»
- Некорректные значения (строки вместо чисел, `NaN`, невалидные отметки времени, значение
  вне шкалы 0–100) не создают наблюдений и не превращаются в нули.

### Интерфейс

Секция анализа (`AnalysisReport`) размещена под отчётом о стадии линии и содержит:
«Наблюдения» (каждое с меткой **«Наблюдение, не оценка»**, источником, периодом и
подтверждениями «поле — значение»), «Рекомендации» (с пояснением недоступности) и
«Ограничения анализа». Расчёт выполняется локально через `analyzePlayer(match, player)`;
при выборе другого участника содержимое обновляется **без новых запросов** к OpenDota.

## Схема Supabase и RLS (Task 10)

Задача — подготовить безопасную схему PostgreSQL для профилей и приватных отчётов
с доступом только владельцу через RLS. **Миграция подготовлена, но не применена**:
применение требует аудита фактической схемы и явного разрешения владельца проекта.

### Аудит фактической базы (read-only)

- **Первый аудит (ассистент, PostgREST с публичным ключом):** запросы к `public.profiles`
  и `public.match_reports` возвращают `404 PGRST205` «Could not find the table … in the
  schema cache» — таблиц в публичной схеме **нет**. Контрольный запрос к заведомо
  отсутствующей таблице даёт тот же код, а существующая таблица с включённым RLS вернула бы
  `200` с пустым массивом.
- **Полный аудит (владелец, SQL Editor, read-only `supabase/inspection/read_only_schema_audit.sql`)** —
  подтверждено:
  - в схеме `public` **нет ни одной таблицы**;
  - `supabase_migrations.schema_migrations` **отсутствует** — CLI-миграции не применялись;
  - пользовательских триггеров на `auth.users` **нет**;
  - функций `public.handle_new_user()` и `public.match_reports_set_updated_at()` **нет**;
  - в `auth.users` зарегистрирован **ровно один** пользователь.
- **Вывод:** конфликтов с существующей схемой нет; приложение использовало только Supabase Auth,
  существующие данные не затрагиваются. Единственный существующий пользователь получит строку
  профиля через backfill (см. «Backfill профилей существующих пользователей»), будущие
  регистрации — через триггер `on_auth_user_created`.
- Миграция `20261014_dotaz_initial.sql`, упоминавшаяся в ранних документах, в репозитории
  **отсутствует** (проверено: ни одного `.sql`-файла в проекте не было).
- Скрипт аудита исправлен: пункт 9 теперь сначала проверяет наличие схемы
  `supabase_migrations` через `to_regclass(...)`, поэтому он выполняется без ошибок и тогда,
  когда CLI-миграции не применялись (как в этом проекте). Скрипт остаётся строго read-only:
  только `SELECT` и один `DO`-блок с `RAISE NOTICE`.

### Таблицы

**`public.profiles`** — одна строка на пользователя:

| Колонка | Тип | Ограничения |
|---|---|---|
| `id` | `uuid` | `primary key`, `references auth.users(id) on delete cascade` |
| `nickname` | `text` | необязательный отображаемый ник |
| `created_at` | `timestamptz` | `not null default now()` |

**`public.match_reports`** — приватные отчёты о матчах:

| Колонка | Тип | Ограничения / назначение |
|---|---|---|
| `id` | `uuid` | `primary key default gen_random_uuid()` |
| `user_id` | `uuid` | `not null`, `references auth.users(id) on delete cascade` |
| `match_id` | `text` | `not null` — **строка**: ID OpenDota может превышать безопасный диапазон JS-чисел, числовое хранение потеряло бы точность |
| `status` | `text` | `not null default 'pending'`, `check (status in ('pending','ready','partial','error'))`; для `ready` требуется заполненный payload (`match_reports_ready_requires_payloads`) |
| `match_payload` | `jsonb` | нормализованный матч и все участники (`NormalizedMatch`, Task 6) |
| `analysis_payload` | `jsonb` | наблюдения, рекомендации и ограничения по всем участникам (Task 9) |
| `rules_version` | `text` | версия правил анализа (например, `1.0.0`) |
| `source` | `text` | `not null default 'OpenDota'` — атрибуция источника |
| `fetched_at` | `timestamptz` | фактическое время получения данных; `NULL`, если не зафиксировано (не подделывается) |
| `created_at` | `timestamptz` | `not null default now()` |
| `updated_at` | `timestamptz` | `not null default now()`, обновляется триггером при изменении строки |

Ограничение уникальности: `unique (user_id, match_id)` (`match_reports_user_match_unique`) —
один отчёт на пару «пользователь + матч»; разные пользователи могут хранить один и тот же
`match_id`. Индекс `match_reports_user_created_idx (user_id, created_at desc)` — для личной истории.

Статусы: `pending` (ожидает расчёта — **значение по умолчанию**), `ready` (полный),
`partial` (частичный отчёт — часть данных провайдера недоступна; отсутствующие значения
остаются `null`, а не нулями), `error` (ошибка расчёта). Фоновой обработки нет.

Статус по умолчанию — `pending`, а не `ready`: строка отчёта, у которой ещё нет payload,
не должна выглядеть завершённым отчётом. Дополнительно ограничение
`match_reports_ready_requires_payloads` запрещает `status = 'ready'` при пустых
`match_payload`/`analysis_payload` — «готовый» отчёт всегда содержит фактические данные.
Колонки payload остаются nullable: это необходимо для состояний `pending`, `partial` и
`error` (миграция не подставляет нули и не выдумывает данные). Строк в `match_reports`
эта миграция не создаёт вообще — таблицу наполняет только Task 11 по реальным данным.

Триггеры:
- `match_reports_set_updated_at` — обновляет `updated_at` и **прерывает** попытку изменить
  `user_id` (исключение «владелец отчёта неизменяем»), чтобы триггер нельзя было использовать
  для обхода проверки владельца;
- `on_auth_user_created` (на `auth.users`) — создаёт строку профиля при регистрации
  (`security definer`, `set search_path = ''`, функция недоступна для вызова из API);
  регистрация и подтверждение email не изменяются.

### Backfill профилей существующих пользователей

Триггер `on_auth_user_created` покрывает только **будущие** регистрации. Для пользователей,
зарегистрированных до применения миграции (аудит подтвердил ровно одного такого пользователя),
миграция выполняет идемпотентный backfill в разделе 3.3:

```sql
insert into public.profiles (id)
select id
from auth.users
on conflict (id) do nothing;
```

- Копируется только `id`; `nickname` не задаётся и остаётся `null` — профиль создаётся без
  выдуманных данных, персональные данные не собираются.
- `on conflict (id) do nothing` (а не `do update`): повторный запуск ничего не меняет,
  существующие строки профилей **не перезаписываются** (`nickname`, `created_at` сохраняются),
  дубликаты невозможны (PK `profiles.id`); удаления (`DELETE`) в миграции нет вообще.
- Backfill не создаёт строк в `match_reports` — таблица отчётов остаётся пустой до Task 11.
- Порядок в миграции: `create table profiles` → триггер регистрации → backfill → политики RLS,
  поэтому к моменту включения политик профили уже на месте (RLS применяется к API, а не к
  владельцу миграции; backfill выполняется от административной роли).
- Будущие регистрации продолжают создавать профиль через `handle_new_user` — поведение
  триггера не изменялось.

### Политики RLS

RLS включён на обеих таблицах; доступ — только владельцу по `auth.uid()`; роль `anon`
лишена привилегий (`revoke all`), права выданы только роли `authenticated`.

| Таблица | Операция | Политика | Условие |
|---|---|---|---|
| `profiles` | SELECT | `profiles_select_own` | `using (auth.uid() = id)` |
| `profiles` | INSERT | `profiles_insert_own` | `with check (auth.uid() = id)` |
| `profiles` | UPDATE | `profiles_update_own` | `using (auth.uid() = id)` + `with check (auth.uid() = id)` |
| `profiles` | DELETE | — | политика не создаётся: удаление профиля продуктом не поддерживается |
| `match_reports` | SELECT | `match_reports_select_own` | `using (auth.uid() = user_id)` |
| `match_reports` | INSERT | `match_reports_insert_own` | `with check (auth.uid() = user_id)` |
| `match_reports` | UPDATE | `match_reports_update_own` | `using (auth.uid() = user_id)` + `with check (auth.uid() = user_id)` |
| `match_reports` | DELETE | `match_reports_delete_own` | `using (auth.uid() = user_id)` |

`user_id` никогда не берётся из данных клиента как доказательство владения: и INSERT,
и UPDATE проверяют `auth.uid()`. Политик с `using (true)` и анонимного доступа нет.
Административный доступ (`service_role`, SQL Editor) обходит RLS по дизайну Supabase и
является служебным — в браузерном коде он не используется.

### Живая проверка RLS

Проверка выполняется **обычными пользовательскими сессиями** (без административных прав и
`service_role`) — только так видны реальные политики.

| Что проверено | Как | Результат |
|---|---|---|
| Анонимный доступ без сессии | REST-запросы с публичным ключом к `profiles` и `match_reports` | **PASS**: `401 / 42501 permission denied` для SELECT/INSERT/UPDATE/DELETE; контрольная несуществующая таблица → `404 PGRST205` (таблицы есть, права `anon` отозваны) |
| Изоляция владельца (SELECT/INSERT/UPDATE/DELETE), вставка с чужим `user_id`, смена владельца, один `match_id` у двух пользователей, дубликат `(user_id, match_id)`, ограничения NOT NULL/CHECK, чтение своего профиля | `supabase/inspection/rls_live_check.mjs` двумя сессиями User A и User B | **NOT RUN** — запуск выполняет владелец (пароли в чат не передаются) |
| Повторный запуск backfill (кейс 17) | SQL Editor, административная роль | **NOT RUN** |
| Профиль пользователя, созданного после миграции (кейс 18) | скрипт + `DOTAZ_USER_C_*` | **NOT RUN** |

Запуск (PowerShell, из корня проекта; пароли не сохраняйте в файлы):

```powershell
$env:DOTAZ_USER_A_EMAIL='dotaz-test-a@example.com'
$env:DOTAZ_USER_A_PASSWORD='<пароль A>'
$env:DOTAZ_USER_B_EMAIL='dotaz-test-b@example.com'
$env:DOTAZ_USER_B_PASSWORD='<пароль B>'

```

Скрипт использует изолированный `match_id = 9999999999`, создаёт строки только со статусом
`pending`, печатает PASS/FAIL/NOT RUN по каждому кейсу и **не удаляет** тестовые строки:
очистка — только по явному решению владельца (`--cleanup`). Подробности — в
`supabase/inspection/rls_verification_plan.md`.

## Личные отчёты (Task 11)

Задача — автоматически сохранять разбор матча в личную историю и **повторно использовать
уже сохранённый отчёт** без дублирования строк и без скрытого пересчёта.

### Жизненный цикл отчёта

| Шаг | Что происходит | Файл |
|---|---|---|
| 1 | Валидация ID матча (без изменений с Task 5) | `src/lib/opendota.ts` |
| 2 | Ожидание достоверного состояния сессии (`loading` → `authenticated`/`anonymous`) | `src/contexts/AuthContext.tsx`, `src/pages/MatchPage.tsx` |
| 3 | Поиск личного отчёта в `match_reports` (только своя строка) | `src/lib/matchReportsSupabase.ts` |
| 4 | Нет отчёта → запрос матча у OpenDota, нормализация (Task 6) | `src/lib/opendota.ts`, `src/lib/normalizeMatch.ts` |
| 5 | Анализ **всех** участников существующим движком (Task 9) | `src/lib/analysisRules.ts` |
| 6 | Сборка одного снимка и вставка строки (`insert`, без upsert) | `src/lib/matchReports.ts` |
| 7 | Показ сохранённого снимка; выбор игрока — локальное состояние | `src/pages/MatchPage.tsx` |

Оркестрация вынесена в `src/lib/matchReportFlow.ts` и не содержит React: зависимости
(сервис, HTTP-клиент, время, состояние сессии) передаются снаружи, поэтому сценарии
проверяются юнит-тестами без живой базы.

### Первое создание отчёта

1. `MatchPage` ждёт состояние сессии; пока оно неизвестно (`loading`), **ни чтений, ни
   записей** не выполняется — показывается «Проверяем состояние сессии…».
2. Для аутентифицированного пользователя выполняется поиск строки по паре
   `(user_id = auth.uid(), match_id)`. Отчёт ищется по владельцу из сессии; `user_id`
   никогда не берётся из URL, форм, локального хранилища или payload.
3. Если отчёта нет — матч запрашивается у OpenDota (`GET /api/matches/{id}`), ответ
   нормализуется (Task 6), затем для каждого участника выполняется анализ (Task 9).
4. Собирается **один** снимок: весь матч (все участники, их статистика и данные линии
   00:00–15:00) и разбор каждого участника. Выбор игрока в интерфейсе на сохранение не влияет.
5. Строка вставляется обычным пользовательским клиентом Supabase под RLS; после успешной
   вставки в интерфейсе появляется «Новый отчёт сохранён».

### Повторное открытие того же матча

- Сохранённый отчёт со статусом `ready` или `partial` используется **сразу**:
  запрос к OpenDota не отправляется, правила не пересчитываются, новая строка не создаётся.
- Показываются сохранённые наблюдения и подтверждения, сохранённая версия правил,
  сохранённые временные метки (`fetched_at`, `created_at`, `updated_at`) и идентификатор строки.
- Доступен выбор любого участника из сохранённого снимка — без обращений к сети и к базе.
- В интерфейсе отображается «Сохранённый отчёт: OpenDota не запрашивалась, наблюдения не
  пересчитывались».

### Владение и приватность

- Чтение и запись выполняются **обычным** клиентом Supabase (publishable-ключ + сессия
  пользователя). Сервисный ключ (`service_role`) в браузерном коде не используется.
- Серверные политики RLS из Task 10 остаются вторым независимым барьером: `auth.uid() = user_id`
  в `USING` и `WITH CHECK`.
- Если клиент по ошибке вернёт строку другого пользователя, сервис отклонит её
  («Полученная запись принадлежит другому пользователю») — данные не будут показаны.
- Гостевой режим сохраняется: анализ показывается, но отчёт не сохраняется, и интерфейс
  честно сообщает: «Гостевой режим: отчёт не сохраняется» + ссылка на вход.

### Формат сохранённых данных

`match_payload` (снимок матча):

```json
{
  "snapshot_version": 1,
  "match": { "match_id": "9007760151", "duration": 2069, "radiant_win": true, "players": [] },
  "limitations": [{ "code": "players.incomplete", "text": "…" }]
}
```

- `match_id` хранится **точной строкой** (числовые преобразования не выполняются: большие ID
  не теряют точность);
- сохраняются **все** участники со всеми полями нормализованной модели (Task 6), включая данные
  линии 00:00–15:00 (Task 8) и корректные `null`;
- `limitations` — честные ограничения данных, обнаруженные при сборке снимка.

`analysis_payload` (снимок анализа):

```json
{
  "snapshot_version": 1,
  "rules_version": "1.0.0",
  "players": [{ "player_slot": 0, "analysis": { "observations": [], "recommendations": [] } }]
}
```

- разбор **каждого** участника движком Task 9: наблюдения с подтверждениями, рекомендации
  (в v1 — пустой список с пояснением), ограничения, идентификаторы правил, версия правил;
- при чтении ничего не досчитывается: сохранённый снимок — источник истины.

Метаданные строки: `rules_version` (версия правил на момент анализа), `source = 'OpenDota'`,
`fetched_at` — фактическое время успешного ответа OpenDota (`null`, если время не зафиксировано),
`status` — по фактической полноте данных.

### Статусы и частичные отчёты

| Статус | Когда выставляется |
|---|---|
| `ready` | ID матча совпадает с запрошенным, известны длительность и победитель, есть хотя бы один участник |
| `partial` | Отчёт содержит подтверждённые данные, но часть сведений провайдера отсутствует (нет длительности, победителя или списка участников) |
| `pending` / `error` | Задачей не создаются; встреченная такая строка **не перезаписывается** (см. ниже) |

Успешный HTTP-ответ OpenDota сам по себе не делает отчёт полным: полнота определяется наличием
конкретных полей. Отсутствующие показатели сохраняются как `null` и никогда не подменяются нулём;
легитимный `0` сохраняется как `0`. Для частичного отчёта интерфейс показывает отдельное
пояснение и список ограничений сохранённых данных.

### Уникальность, гонки и незавершённые записи

- Один отчёт на пару `(user_id, match_id)` обеспечивает ограничение `UNIQUE (user_id, match_id)`
  из Task 10: повторная вставка отклоняется с кодом `23505`.
- Алгоритм — **вставка с восстановлением после конфликта**, без `upsert` и без перезаписи.
  Если два почти одновременных запроса не нашли отчёт, оба сформируют снимок, но строка создастся
  только одна: второй запрос получит `23505`, перечитает существующую строку и покажет её.
  Снимок победителя не изменяется.
- Автоматических повторов и опроса нет: повтор возможен только по явному действию пользователя
  (кнопка «Повторить сохранение»).
- **Ограничение:** схема не реализует очередь обработки или распределённую аренду (lease), поэтому
  состояние `pending` этой задачей не используется, а встреченная `pending`/`error`-строка не
  перезаписывается и не удаляется — пользователь видит честное сообщение и свежий расчёт без записи
  в базу. Durable-очередь потребовала бы изменений схемы и отдельного согласования с владельцем.

### Версии правил анализа

- В отчёт записывается фактическая версия правил (`ANALYSIS_RULES_VERSION`, сейчас `1.0.0`) и
  дублируется внутри `analysis_payload`.
- При открытии сохранённого отчёта наблюдения берутся **из снимка**, а не пересчитываются текущим
  кодом; строка автоматически не обновляется.
- Если сохранённая версия отличается от текущей, выводится фактическое уведомление: «Отчёт сохранён
  с версией правил анализа X; текущая версия правил — Y. Показаны сохранённые наблюдения без
  пересчёта». Автоматическая миграция отчётов не реализована.

### Поведение при сбое базы данных

- Виды ошибок различаются явно: конфликт уникальности, отсутствие прав (RLS), истёкшая сессия,
  сеть, повреждённый снимок, прочие. Ошибка прав не превращается в «отчёт не найден».
- Если анализ сформирован, но запись не удалась, показывается «Отчёт сформирован, но сохранить его
  не удалось» с причиной и кнопкой повторного сохранения. Такой отчёт **не** выдаётся за сохранённый:
  у него нет `id` и временных меток.
- Если чтение базы не удалось, отчёт вслепую не сохраняется (иначе возможен дубликат) — показывается
  свежий анализ с предупреждением.
- Если сохранённый снимок повреждён или имеет неизвестную версию формата, строка не перезаписывается
  и не удаляется — выводится понятная ошибка с пояснением, что запись не изменялась.

сортировка, переходы к матчам и состояния пустой истории реализованы в Task 12 — см. раздел
«Личная история (Task 12)».

## Личная история (Task 12)

Приватная страница `/history` показывает **только собственные** сохранённые отчёты
пользователя и позволяет вернуться к ним.

### Маршрут и защита

- Маршрут `/history` обёрнут в `ProtectedRoute` (Task 4): гости перенаправляются на
  `/login` с возвратом на исходный адрес после входа; приватные данные не показываются.
- Идентичность берётся исключительно из проверенной сессии Supabase (`useAuth`); ID
  пользователя не читается из URL, форм или локального хранилища.
- Все запросы к `match_reports` ограничены фильтром `user_id = <id из сессии>`; серверные
  RLS-политики Task 10 остаются вторым независимым барьером.
- `service_role` и административные ключи не используются: применяется обычный клиент с
  publishable-ключом и сессией пользователя.

### Что показывает карточка отчёта

| Поле | Источник | Поведение при отсутствии |
|---|---|---|
| ID матча | `match_id` (точная строка) | карточка без ID не создаётся — запись пропускается |
| Дата сохранения | `created_at` | «Нет данных» |
| Результат матча | `match_payload->match->>radiant_win` сохранённого снимка | «Нет данных» (результат никогда не выводится из статистики игроков) |
| Статус | `status` | «Полный отчёт», «Частичный отчёт», «Ожидает расчёта», «Ошибка расчёта» |
| Источник | `source` | значение не выдумывается |
| Версия правил | `rules_version` | «не указана» |

Внутренние UUID строк в интерфейсе не показываются: основным идентификатором служит ID матча.

### Запрос к базе

- Загружаются **только метаданные карточки** (`id`, `user_id`, `match_id`, `status`,
  `source`, `rules_version`, `created_at`, `fetched_at` и результат матча через JSON-путь).
  Тяжёлые JSONB-payload (`match_payload`, `analysis_payload`) в список не тянутся.
- Одна страница истории — **один запрос**; запросов «по одному на элемент» нет.
- Метаданные проверяются строго: строки с непригодным форматом или чужим `user_id`
  пропускаются, список продолжает отображаться, а в интерфейсе появляется честное
  сообщение о числе пропущенных записей (данные не изменяются и не удаляются).

### Сортировка и пагинация

- Сортировка выполняется **в базе** до пагинации: `created_at DESC`, затем `id DESC` как
  устойчивый вторичный ключ (при одинаковых отметках времени порядок детерминирован).
- По умолчанию — новые отчёты первыми.
- Размер страницы — `HISTORY_PAGE_SIZE` (20). Если вернулась полная страница, под списком
  появляется сообщение «Показаны последние N отчётов… список не является полным» и кнопка
  «Показать ещё», которая догружает следующую страницу через `offset` (`.range(...)`).
  Список **не** выдаётся за полный, и старые отчёты не теряются молча.
- Сортировка и пагинация не изменяют и не пересоздают отчёты.

### Статусы отчётов

| Статус | Отображение | Действие |
|---|---|---|
| `ready` | «Полный отчёт» | «Открыть отчёт» → `/matches/:matchId` |
| `partial` | «Частичный отчёт» | «Открыть отчёт» → `/matches/:matchId` |
| `pending` | «Ожидает расчёта» | открытие недоступно (фактическое состояние) |
| `error` | «Ошибка расчёта» | открытие недоступно (фактическое состояние) |

Для `pending`/`error` ссылка открытия не выводится: страница матча не может показать такой
отчёт как готовый (Task 11 честно сообщает о незавершённой записи). При просмотре истории
никакие отчёты не пересчитываются, не перезаписываются и не удаляются.

### Состояния страницы

- **Загрузка** — «Загружаем историю анализов…».
- **Пустая история** — «У вас пока нет сохранённых анализов.» + ссылка «Проанализировать матч»
  на главную.
- **Ошибка базы данных** — «Не удалось загрузить историю анализов.» с причиной и кнопкой
  «Повторить загрузку»; пустая история в этом случае **не** показывается.
- **Гость** — редирект на `/login` (через `ProtectedRoute`); на самой странице предусмотрено
  нейтральное сообщение без приватных данных.
- **Сессия восстанавливается** — «Проверяем вашу сессию…»; данные не запрашиваются.
- **База не настроена** — честное сообщение о недоступности сохранённой истории.

### Переход к сохранённому отчёту

Ссылка карточки ведёт на `/matches/:matchId`. Далее работает Task 11: сохранённый снимок
загружается **без нового запроса к OpenDota**, без пересчёта наблюдений и без вставки новой
строки; идентификатор отчёта и временные метки не меняются, доступен выбор любого участника.
Отдельного маршрута для отчёта история не создаёт.

### Смена аккаунта и устаревшие ответы

- При смене пользователя, выходе или размонтировании страницы список немедленно очищается, а
  все незавершённые запросы инвалидируются: ответ прошлого аккаунта не может быть показан новому.
- Каждый запрос получает токен (`createRequestGuard`); применяется только ответ последнего
  запроса, поэтому «догоняющий» ответ после повторной попытки или смены аккаунта отбрасывается.
- Приватность не полагается только на RLS: устаревшие данные удаляются из состояния интерфейса.

## Локализация RU/EN (Task 13)

Интерфейс полностью поддерживает русский (`ru`) и английский (`en`). Русский — язык по
умолчанию; выбор пользователя сохраняется в `localStorage` под ключом `dotaz.locale`
(это пользовательская настройка, а не данные аутентификации: отчёты, матчи и сессии там
не хранятся). При недоступном хранилище (приватный режим, запрет записи) интерфейс
продолжает работать, язык действует только в текущей сессии.

Переключатель RU/EN находится в шапке сайта (`src/components/LanguageSwitcher.tsx`):
кнопки доступны с клавиатуры, состояние объявляется через `aria-pressed`, подписи
читаются скринридером, активная кнопка подсвечена красным акцентом. Переключение
мгновенное: страница не перезагружается, запросы к OpenDota не отправляются, отчёты не
пересохраняются, анализ не пересчитывается, выбранный игрок и текущий маршрут сохраняются.
Выбранный язык применяется к `<html lang>` через `document.documentElement.lang`.

### Архитектура

| Файл | Назначение |
|---|---|
| `src/i18n/translations.ts` | Русский словарь (базовый, из него выводится тип `TranslationKey`), сборка словарей, `interpolate`, `isLocale` |
| `src/i18n/translationsEn.ts` | Английский словарь; обязан содержать те же ключи (паритет проверяется тестами) |
| `src/i18n/I18nContext.tsx` | `I18nProvider`, `useI18n`, хранение выбора, `document.documentElement.lang` |
| `src/i18n/formatters.ts` | Даты (UTC с явной меткой), числа и проценты с учётом локали |
| `src/i18n/analysisText.ts` | Локализация наблюдений, периодов, ограничений и пояснения о рекомендациях |
| `src/i18n/viewLabels.ts` | Подписи представления (стороны, победитель, слот, K/D/A, длительность) |
| `src/i18n/errors.ts` | Стабильные коды ошибок OpenDota, валидации ID и Supabase Auth → тексты RU/EN |

Компоненты, отрисованные без провайдера (например, в изолированных SSR-тестах),
получают русский словарь по умолчанию — поэтому локализация не меняет поведение
существующих проверок.

### Локализация сохранённых отчётов

Снимки отчётов (JSONB) **не изменяются** при смене языка: `rule_id`, `rule_version`,
`evidence`, метрики, периоды и значения остаются прежними. Для отображения:

- для известных правил версии `1.0.0` текст собирается заново по `rule_id` и сохранённым
  подтверждениям (`evidence`) — значения подставляются из снимка, ничего не пересчитывается;
- для неизвестного `rule_id` или версии показывается сохранённый текст с честной пометкой
  «Перевод недоступен: сохранённый текст показан как есть (правило …, версия …)»;
- известные коды ограничений локализуются по коду, неизвестные сохраняют исходный текст;
- пояснение о недоступности рекомендаций и периоды (`весь матч` / `00:00–15:00`) локализуются;
- технические идентификаторы (`lh_t[15]`, `gold_t[15]`, `xp_t[15]`, `lane_efficiency_pct`,
  `kills_log`, `deaths_log`, `purchase_log`, `rule_id`, `match_id`) не переводятся.

### Ссылки навигации и состояния доступа

Все ссылки и служебные состояния локализованы через словарь:

- «← Вернуться на главную» / «← Back to Home» (`common.backHome`) — в том числе ссылка
  рядом с личным отчётом на странице матча (дефект, найденный при ручной проверке в
  браузере, исправлен);
- «Войти в аккаунт» / «Log in» (`persistence.guest.loginLink`) — ссылка входа в гостевом
  режиме в панели личного отчёта;
- «Проверка доступа» / «Access check», «Проверка авторизации…» / «Checking authorization…»
  (`auth.guard.*`) — состояние проверки сессии в `ProtectedRoute` (маршрут `/history`).

Регрессия закреплена тестами `src/pages/matchPage.test.tsx` и
`src/components/protectedRoute.test.tsx`: они проверяют значения ключей в RU и EN,
отсутствие русских литералов в исходниках и SSR-рендер без кириллицы в английской локали.

### Ошибки, даты и числа

- Классы ошибок сохраняются: 403 от OpenDota не превращается в «матч не найден», ошибка
  прав не становится «отчёта нет». Локализуется только текст, секреты не показываются.
- Временные метки выводятся в UTC с явной меткой (`2026-10-21 09:30 UTC` для RU,

## Автоматическая обработка реплея OpenDota (Task 14)

DotaZ сам проверяет, есть ли в ответе матча подробные (replay-derived) данные, и при их
отсутствии автоматически запрашивает обработку реплея. Отдельной кнопки «Запросить
обработку» нет.

### Проверенные endpoint'ы (живая проверка 30.10.2026)

| Запрос | Ответ | Примечание |
| --- | --- | --- |
| `POST https://api.opendota.com/api/request/{match_id}` | `200 {"job":{"jobId":614710125}}` | работает без ключа; CORS разрешён (`Access-Control-Allow-Origin` повторяет Origin, `OPTIONS` → `204`) |
| `GET https://api.opendota.com/api/request/{job_id}` | `200` + `{"job":{"status":"pending" \| "in progress" \| "completed" \| "failed"}}` | тело `null` означает «задача не найдена», а не «данные готовы» |

Анонимные лимиты видны в заголовках ответа: `X-Rate-Limit-Remaining-Minute: 59`,
`X-Rate-Limit-Remaining-Day: 2998` (60 запросов в минуту и 3000 в сутки). Реплеи OpenDota
хранит около 10 дней (ответ мейнтейнера в `odota/core#2275`), поэтому матчи старше окна
хранения не парсятся: запрос по ним даже не отправляется.

Ключ `api_key` не даёт доступа к приватным данным и служит только для повышения лимитов.
Он читается из необязательной переменной окружения сборки `VITE_OPENDOTA_API_KEY` и никогда
не хранится в исходном коде; без неё запросы идут анонимно. Серверный слой и прокси не
требуются: браузерный доступ подтверждён заголовками CORS. Новых платных сервисов нет.

### Жизненный цикл

1. Открывается страница матча и проверяется сохранённый отчёт пользователя.
2. Если сохранённый отчёт уже содержит подробные данные — он используется без обращений к OpenDota.
3. Иначе загружается матч и проверяется полнота: журнал покупок (`purchase_log`) и таймлайны
   (`lh_t`, `gold_t`, `xp_t`, `kills_log`, `deaths_log`) у всех участников.
4. При отсутствии подробностей и доступном реплее отправляется запрос обработки (не более двух
   запросов на матч); статус опрашивается с backoff (4 с → 8 с → 15 с) — не более восьми опросов
   и не более 90 секунд на сессию.
5. После статуса `completed` матч загружается повторно и полнота проверяется заново: успех
   объявляется только при подтверждённых подробных данных.
6. Результат сохраняется в Supabase; при следующем открытии используется сохранённый отчёт.

### Честные статусы и ограничения

- Реплей недоступен или удалён → «Реплей недоступен. Показана доступная статистика.»
- Обработка не завершилась за сессию → «OpenDota продолжает обработку реплея…»; идентификатор
  задачи сохраняется в `localStorage` (`dotaz.parse.attempt.<match_id>`), и при следующем
  открытии страницы наблюдение продолжается. Фоновая обработка не обещается.
- Ограничение частоты, сетевые сбои и сбои провайдера показываются отдельными сообщениями;
  подробные данные не выдумываются.
- Дубликаты не создаются: активная задача переиспользуется; уход со страницы отменяет опрос.

### Предметы за матч и покупки интервала

Политики двух секций различаются (`src/lib/items.ts`): в интервале 00:00–15:00 показываются
компоненты, собранные предметы, исключения (Bottle, Aghanim's Shard, Refresher Shard, Cheese,
Block of Cheese; ключ Block of Cheese — `royale_with_cheese`) и неклассифицированные ключи; в
секции за весь матч — только собранные предметы, Bottle и базовые Boots of Speed без
подтверждённого улучшения. Обычные расходники, рецепты и (в секции за матч) компоненты и
исключения ранней стадии скрыты. Неизвестный ключ в интервале показывается как есть, в секции
за матч — скрывается. Время — первая подтверждённая покупка предмета; момент сборки может
отличаться от момента покупки последнего компонента. Сырые журналы покупок в нормализованных
данных и сохранённых снимках не изменяются. Имена предметов выводятся дословно как `dname`
OpenDota (например, `ultimate_scepter` → «Aghanim's Scepter»).

### Обновление сохранённых отчётов

Отчёты, сохранённые до Task 14 (снимок без журнала покупок и таймлайнов), не блокируют
автоматическую обработку: после подтверждённого улучшения строка обновляется — только своя,
по паре `user_id` + `match_id`, без дубликатов. Перезапись выполняется только при строгом
улучшении данных; если новые данные неполные или хуже, сохранённый отчёт остаётся как есть.
Схема и RLS не менялись: обновление опирается на уже существующую политику
`match_reports_update_own`; миграции для Task 14 не требуются.

1. **token_hash** (рекомендуемый для шаблонов):

2. **Confirmation URL** (значение по умолчанию): `{{ .ConfirmationURL }}` — при этом
   используется PKCE-код (`?code=...`) или implicit-переход с токенами в hash,
   которые обрабатывает официальный клиент.

Проверьте, что итоговый адрес из письма попадает в список Redirect URLs проекта.

## Известные проблемы и ограничения

1. **Живая проверка аутентификации не выполнялась** (`NOT RUN`): фактическая регистрация, вход, восстановление сессии, выход и переход по ссылке подтверждения не тестировались с реальным проектом Supabase — нужны настроенный проект и тестовые аккаунты (см. «Что проверено, а что нет»).
2. **Защита маршрутов действует только на клиенте** (Task 4): `/history` защищён на уровне интерфейса. Серверные политики RLS **применены владельцем**, но изоляция данных между пользователями **ещё не проверена живыми сессиями** (кейсы 1–12, 14–16, 18 — `NOT RUN`), поэтому до завершения проверки данные истории нельзя считать защищёнными одной лишь клиентской проверкой.
3. **Живая проверка сохранения личных отчётов не выполнялась** (Task 11, `NOT RUN`): сценарии «первый анализ → сохранение», «повторное открытие без запроса к OpenDota», «второй пользователь видит только свой отчёт» и «гонка двух запросов» проверены только юнит-тестами с подменой клиента таблицы и HTTP-клиента.
