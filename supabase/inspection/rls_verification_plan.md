# DotaZ — план проверки RLS (Task 10)

Документ описывает, как проверить политики доступа после применения миграции
`supabase/migrations/20261018120000_dotaz_profiles_match_reports.sql`.

> **Важно:** проверка выполняется от имени **обычных аутентифицированных пользователей**
> (User A и User B). SQL Editor и клиент с `service_role` работают в обход RLS и для
> проверки политик **не подходят**. Токены и пароли не передаются в чат и не сохраняются
> в репозитории.

## Подготовка

1. Убедитесь, что миграция применена владельцем (см. README, раздел Task 10).
2. Создайте двух тестовых пользователей через приложение или Supabase Dashboard
   (Authentication → Users): `dotaz-test-a@example.com` и `dotaz-test-b@example.com`.
3. Выполните вход каждым пользователем в приложении DotaZ (браузер хранит сессию Supabase
   локально, токены не покидают браузер).
4. Тестовые записи создавайте только для пары `(user_id, match_id)` с явно тестовым ID,
   например `9999999999`. Реальные отчёты пользователей не изменяйте и не удаляйте.
5. Проверьте backfill: число строк `public.profiles` должно совпадать с числом пользователей
   в `auth.users`; у пользователей, зарегистрированных до миграции, `nickname` = NULL
   (миграция не выдумывает данные). `select count(*) from public.profiles;`

## Проверяемые случаи

| № | Действие | Ожидаемый результат |
|---|---|---|
| 1 | User A читает свой профиль (`profiles` где `id = auth.uid()`) | Возвращается 1 строка |
| 2 | User A пытается прочитать профиль User B | 0 строк (RLS не отдаёт чужую строку) |
| 3 | User A создаёт отчёт с `match_id = 9999999999` | Вставка успешна |
| 4 | User B создаёт отчёт с тем же `match_id` | Вставка успешна (уникальность в рамках пользователя) |
| 5 | User A читает свой отчёт | Возвращается его строка |
| 6 | User B читает отчёт User A | 0 строк |
| 7 | User B обновляет отчёт User A (`status` или payload) | 0 строк обновлено |
| 8 | User B удаляет отчёт User A | 0 строк удалено |
| 9 | User B вставляет отчёт с `user_id` User A | Ошибка политики (`new row violates row-level security policy`) |
| 10 | User B пытается сменить `user_id` своего отчёта на User A | Ошибка: либо политика (`WITH CHECK`), либо исключение триггера «владелец отчёта неизменяем» |
| 11 | User A повторно вставляет `(свой user_id, 9999999999)` | Ошибка уникальности `match_reports_user_match_unique` |
| 12 | Разные пользователи хранят один `match_id` | Разрешено: две строки с разными `user_id` |
| 13 | Анонимный клиент (без сессии, только publishable key) читает `match_reports` | 0 строк или отказ (привилегии `anon` отозваны) |
| 14 | Вставка с пустым `match_id` / без `user_id` / `status` вне списка | Ошибка ограничения (NOT NULL / CHECK) |
| 15 | Прямой запрос к таблице от User A с фильтром по `user_id` User B | 0 строк |
| 16 | Пользователь, зарегистрированный **до** применения миграции, читает свой профиль | Ровно 1 строка (создана backfill-разделом 3.3); `nickname` = NULL, `created_at` = время применения миграции |
| 17 | Повторный запуск раздела 3.3 (backfill) вручную от административной роли | Число строк не изменилось, `nickname`/`created_at` прежних строк не перезаписаны (`on conflict (id) do nothing`) |
| 18 | Регистрация нового пользователя (User C) после применения миграции | Через триггер `on_auth_user_created` появляется ровно 1 строка профиля с `id` нового пользователя |

## Автоматизированная проверка скриптом (рекомендуется)

Кейсы 1–16 и 18 выполняются одним скриптом `supabase/inspection/rls_live_check.mjs`.
Он входит **обычными** пользовательскими сессиями (`signInWithPassword`) с публичным
ключом; service-role не используется, пароли берутся только из переменных окружения
процесса и никогда не печатаются.

```powershell
# из корня проекта; пароли НЕ сохраняйте в файлы и не коммитьте
$env:DOTAZ_USER_A_EMAIL='dotaz-test-a@example.com'
$env:DOTAZ_USER_A_PASSWORD='<пароль A>'
$env:DOTAZ_USER_B_EMAIL='dotaz-test-b@example.com'
$env:DOTAZ_USER_B_PASSWORD='<пароль B>'
node supabase/inspection/rls_live_check.mjs
```

- URL и publishable-ключ берутся из `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY`
  (или из локального `.env`; пароли из `.env` не читаются).
- Кейс 18 проверяется, если дополнительно заданы `DOTAZ_USER_C_EMAIL` / `DOTAZ_USER_C_PASSWORD`
  (пользователь, зарегистрированный **после** применения миграции).
- Кейс 17 (повторный запуск backfill) требует административной роли → помечается `NOT RUN`
  и выполняется владельцем вручную в SQL Editor.
- Скрипт использует только изолированный `match_id = 9999999999` и создаёт отчёты со
  статусом `pending` (готовые отчёты не выдумываются).
- **Удаление тестовых строк по умолчанию не выполняется.** Очистка — только по явному
  решению владельца: повторный запуск с флагом `--cleanup` (удаляются лишь собственные
  строки A и B с `match_id = 9999999999`).
- Скрипт печатает `PASS`/`FAIL`/`NOT RUN` по каждому кейсу и код выхода 1 при наличии `FAIL`.

## Как выполнять запросы от имени пользователя

Безопасные способы (сессия пользователя, не административная):

- в приложении DotaZ (браузер, dev-консоль): `supabase.from('match_reports').select('*')`
  — клиент использует сессию текущего пользователя;
- в Supabase Dashboard → SQL Editor можно выполнить
  `select set_config('request.jwt.claims', '{"sub":"<UUID пользователя>"}', true);`
  **только** для диагностики условий политик — это не заменяет проверку через
  реальный клиент, так как роль остаётся административной;
- для независимой проверки используйте Supabase CLI/скрипт с обычным входом
  (`signInWithPassword`) и последующими запросами.

## Очистка

Тестовые строки скрипт по умолчанию **не удаляет**. Удаляйте **только** созданные тестовые
строки и только по явному решению владельца:

```powershell
node supabase/inspection/rls_live_check.mjs --cleanup   # удалит только свои строки A и B с match_id=9999999999
```

Либо вручную (административно, SQL Editor):

```sql
delete from public.match_reports where match_id = '9999999999';
```

Тестовых пользователей удаляет владелец через Dashboard (Authentication → Users).
Реальные отчёты пользователей не трогать.

## Текущий статус

- Аудит схемы: **выполнен полностью** (владелец, SQL Editor, read-only
  `read_only_schema_audit.sql`).
- Применение миграции: **выполнено владельцем**. Подтверждено: `public.profiles` и
  `public.match_reports` существуют, RLS включён на обеих таблицах, семь владельческих
  политик на месте, два пользователя зарегистрированы и оба имеют строки профилей,
  реальных отчётов в `match_reports` пока нет.
- Анонимный доступ (кейс 13): **PASS (выполнено)** — запросы к обеим таблицам без сессии
  отклоняются с `401 / 42501 permission denied` (привилегии `anon` отозваны); контрольный
  запрос к несуществующей таблице даёт `404 PGRST205`, то есть таблицы действительно есть.
- Проверка RLS двумя пользовательскими сессиями (кейсы 1–12, 14–16, 18): **NOT RUN** —
  требует паролей User A/User B, которые в чат не передаются; процедура подготовлена
  (`rls_live_check.mjs`), запуск выполняет владелец.
- Кейс 17 (повторный запуск backfill): **NOT RUN** — требует административной роли.
- Статические тесты артефактов (`src/lib/schemaMigration.test.ts`) проверяют только текст
  SQL/JS-файлов и **не** являются подтверждением поведения живой базы.
