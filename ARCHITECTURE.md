## 1. Стек и архитектурные принципы
- Клиент: React 18, TypeScript, Vite, React Router, CSS, Vitest.
- Учётные записи и постоянное хранение: Supabase Auth + PostgreSQL с RLS.
- Внешние игровые данные: OpenDota API. Запросы загрузки матча и обработки реплея выполняются по фактически подтверждённому API; закрытые ключи в браузер не помещаются.
- Истина: реальные значения API и сохранённые снимки. Отсутствие поля обозначается `null`, не нулём. Наблюдения не приравниваются к оценкам без проверенных норм.
- RU/EN — перевод представления, не модификация фактов и сохранённых снимков.

## 2. Маршруты
- `/` — главная страница, ввод ID, переключение языка.
- `/matches/:matchId` — итог матча, десять игроков, выбор участника, анализ 0–15 минут, предметы, наблюдения и сохранение.
- `/history` — личные отчёты текущего аккаунта; защищён `ProtectedRoute` и RLS.
- `/login`, `/register`, `/auth/confirm` — Supabase Auth.
- `/heroes` — существующая страница, но полноценный актуальный каталог/мета пока не реализованы.
- Неизвестный маршрут — 404.

Task 15 **уже изменила только** `/matches/:matchId`; остальные маршруты не были предметом её редизайна. Новые страницы/разделы Tasks 19–20 пока не реализованы.

## 3. Путь данных матча и обработка реплея
1. Валидация числового ID, проверка состояния авторизации.
2. Поиск личного отчёта в Supabase по `(user_id, match_id)`; подробный сохранённый снимок может использоваться напрямую.
3. При отсутствии достаточных подробных данных — получение данных OpenDota `GET /api/matches/{match_id}` и проверка заполненности.
4. Если подробные поля отсутствуют и обработка доступна — автоматический запрос OpenDota на разбор реплея, ограниченный опрос статуса с backoff, повторное получение матча после успешного завершения.
5. Нормализация → анализ подтверждённых фактов → визуализация → первоначальное сохранение или контролируемое обновление улучшенного личного отчёта.
6. Если реплей недоступен/обработка не завершилась — частичный отчёт с понятным статусом; приложение не должно бесконечно отправлять запросы.

Реализованные модули Task 14: `src/lib/replayParsing.ts`, `opendotaParse.ts`, `matchParseFlow.ts`, `matchReportFlow.ts`, `matchReports.ts`, `matchReportsSupabase.ts`, `items.ts` и компоненты соответствующих панелей. Перед следующей задачей сверять реальные сигнатуры с кодом.

## 4. Нормализация и аналитика
- Данные матча: ID (строка), длительность, победитель, десять игроков с `player_slot`, `hero_id`, K/D/A, GPM, XPM, итоговые LH и прочими реально доступными полями.
- Интервал нового анализа **00:00–15:00**: `lh_t[15]`, `gold_t[15]`, `xp_t[15]`; события от 0 до 900 секунд включительно. Не заменять их полными итоговыми показателями матча.
- Необязательные данные: `kills_log`, `deaths_log`, `purchase_log`, `lane_efficiency_pct`; отсутствие даёт ограничение анализа.
- В новой аналитике правила `1.1.0`; метрики/доказательства относятся к фактическим данным. Неподтверждённых норм героя/роли нет.
- Старые сохранённые отчёты версии 1 корректно обозначают **00:00–10:00**, без переинтерпретации чисел как 15-минутных.

## 5. Правила показа предметов Task 14
**Сырые журналы не фильтруются при сохранении.** Фильтрация — только на уровне представления.

| Раздел | Показывать | Скрывать |
|---|---|---|
| Покупки 00:00–15:00 | Компоненты, готовые предметы, Bottle, Aghanim's Shard, Refresher Shard, Cheese, Block of Cheese | Обычные расходники, варды, Smoke, Dust, TP, рецепты |
| Предметы за весь матч | Значимые готовые предметы, Bottle, базовые Boots of Speed при отсутствии подтверждённого улучшения; Aghanim's Shard как значимое улучшение | Прочие сырые компоненты, обычные расходники, рецепты; Refresher Shard/Cheese/Block of Cheese не включать лишь на основании исключения ранней стадии |

- Сохранять фактический порядок и повторные события в раннем журнале; в сводке полного матча — подтверждённое время первой покупки/получения.
- При улучшении сапог в журнале скрывать базовые Boots of Speed по согласованной логике.
- Название `ultimate_scepter` показывать как **Aghanim's Scepter**; ключ API не переписывать.
- При неизвестном ключе предмета не выдумывать классификацию полноценного предмета.

## 6. Хранение и защита
- `public.profiles`: профиль владельца с привязкой к `auth.users`.
- `public.match_reports`: `id`, `user_id`, `match_id`, `status`, `match_payload`, `analysis_payload`, `rules_version`, `source`, `fetched_at`, `created_at`, `updated_at`.
- Уникальность `(user_id, match_id)`; RLS обеспечивает чтение/запись своих записей.
- Snapshot v2 добавляет `laning.interval` и `purchaseLog`; версии v1/v2 читаются. Неизвестные версии должны отвергаться безопасно.
- Усовершенствованный отчёт заменяет существующий только после валидации улучшения данных, без изменения `user_id` и `match_id`; ошибки сохранения не скрываются.
- Никогда не помещать ключ `service_role` или другой приватный секрет в Vite-клиент. `VITE_*` переменные доступны браузеру.

## 7. Локализация, состояния и ограничения
- RU/EN: словари `src/i18n`, переключатель, локализация UI/ошибок/известных правил; сохранённые отчёты не пересчитываются из-за смены языка.
- Состояния: загрузка, частичный/полный отчёт, обработка реплея, отсутствие реплея, ошибки OpenDota (404, 403, 429, 5xx), авторизация, ошибки Supabase, недоступные показатели.
- Успешная автоматическая обработка любого заданного реплея не гарантирована: требуется его доступность у провайдера.

### 15.2 Предлагаемый поток идентификации

```text
Browser: "Sign in with Steam"
  -> trusted backend: initiate Steam OpenID 2.0 (state/CSRF binding)
  -> Steam: authenticate user
  -> trusted backend callback: validate realm/return_to,
     verify assertion with Steam, nonce/replay and SteamID64
  -> trusted identity mapping: verified SteamID64 <-> existing/new app identity
  -> VERIFIED SUPABASE-COMPATIBLE SESSION (integration method TBD)
  -> Browser: authenticated app session and original destination
  -> Supabase Postgres: auth.uid() + existing RLS -> own reports only
```

Это **контракт потока**, а не доказательство, что механизм выпуска Supabase-сессии уже выбран или доступен. Сессия должна быть создана только поддерживаемым и протестированным способом; самодельный JWT, неподписанный идентификатор или произвольная подмена `auth.uid()` запрещены.

2. Для каждого варианта проверить стоимость, инфраструктуру, модель доверия, refresh/logout и **сохранение старых UUID**. Не утверждать поддержку до проверки.
3. Может ли существующий пользователь привязать SteamID64 к **своему прежнему** UUID без переноса/перезаписи истории? Если нет — это блокер, а не повод создавать новый аккаунт и терять историю.

- Запрос на добавление Steam как провайдера (`supabase/auth` issue #417) закрыт как дубликат общего трекера запросов провайдеров (#451); поддержка Steam не появилась.

Значит для Steam почти наверняка потребуется собственный доверенный серверный компонент (или внешний identity broker), который после проверки OpenID-утверждения приводит пользователя к поддерживаемой Supabase-сессии. Это **не** решение, а обоснованная гипотеза, требующая прототипа и подтверждения на конкретной версии Supabase и выбранной инфраструктуре. ### 15.4 Защита Steam OpenID и жизненного цикла сессии

- Сервер проверяет Steam OpenID assertion через предусмотренную протоколом проверку, ожидаемые `realm` и `return_to`, подлинность Steam endpoint и claimed identifier. Никакого доверия к одному лишь параметру URL, присланному браузером.
- Защита CSRF/state, одноразовость и ограничение срока действия nonce, replay protection, строгие redirect allowlists, защита от open redirect и фиксации сессии.
- SteamID64 проверяется и хранится как **строка**; JS `number` не подходит из-за точности больших целых. Связь SteamID64 ↔ идентификатор приложения должна быть уникальной и защищённой от перепривязки посторонним пользователем.
- HTTPS в production; безопасные cookie (`Secure`, `HttpOnly`, `SameSite` по принятой модели), безопасное хранение/обновление/истечение сессии, корректный выход и инвалидирование при необходимости.
- Серверные секреты, служебные токены и ключи `service_role` никогда не передаются в браузер, `VITE_*`, исходники, Git или публичные логи.
- Нельзя принимать ник, аватар или email как доказательство владения Steam-аккаунтом. Аватар/ник — только отображаемые метаданные, возможны недоступные/приватные данные.
- UI `ProtectedRoute` дополняет, но **не заменяет** RLS. Прямые обращения к Supabase должны проходить те же проверки владельца.

### 15.5 Сохранение существующих пользователей и отчётов

Фактическая схема подтверждена инспекцией 2026-11-10 (см. 15.0): `auth.users` → `public.profiles.id` (`on delete cascade`), `public.match_reports.user_id` (`on delete cascade`), уникальность `(user_id, match_id)`, RLS по `auth.uid() = user_id` и триггер, запрещающий менять `user_id`. **Новые таблицы и столбцы для связи Steam-идентичности сейчас не утверждаются:** их форма определяется после выбора поддерживаемого механизма сессии (15.3), иначе можно зафиксировать несовместимую модель.

**Отдельный риск, который нельзя игнорировать:** каскадное удаление означает, что любой сценарий «удалить и создать пользователя заново» уничтожит сохранённые отчёты. Поэтому удаление пользователей как способ миграции запрещено в рамках Task 20A, а привязка Steam обязана сохранять существующий `auth.users.id`.


Безопасный переход:

1. Пользователь со старым email/password входит в **свой существующий** аккаунт через временный legacy-flow.
2. Пользователь отдельно подтверждает владение Steam через серверный OpenID 2.0.
3. Сервер проверяет, что SteamID64 ещё не связан с чужой учётной записью; только после этого выполняется атомарная защищённая привязка к **прежнему UUID**.
4. Пользователь повторно входит через Steam; тест подтверждает тот же `auth.uid()`, прежние `profiles` и все `match_reports` без изменения `user_id`.
5. Пока не подтверждён безопасный путь привязки и восстановления, legacy-вход для непривязанных пользователей не отключается. Нельзя объединять записи по одинаковому нику/email, автоматически переносить отчёты на новый UUID или удалять старые аккаунты.

Новые Steam-пользователи создаются только по поддерживаемой схеме после проверки OpenID и успешного установления Supabase-сессии. Варианты хранения связи и миграции документируются после реального SQL-аудита, а не угадываются.

### 15.6 Архитектурные границы и проверка

- Не менять данные OpenDota, `match_reports`, снимки v1/v2, правила аналитики и норм, каталог героев или benchmark JSON ради авторизации.
- Нужны unit/integration-тесты верификации и ошибок callback, уникальности SteamID64, отказа при replay/CSRF, логина/логаута/обновления, попыток доступа к чужим данным.
- Нужны реальные E2E-сценарии: новый Steam-пользователь; старый пользователь с привязкой; старый пользователь без привязки; два аккаунта с разными отчётами; неверная/отменённая проверка; мобильный RU/EN; восстановление после перезагрузки.

## 16. Личный профиль Dota 2 — Task 20B (план, 2026-11-10)

**Статус:** `planned`. **Зависимость:** Task 20A и безопасная проверенная связь Steam ↔ пользователь Supabase. Основная Task 20 (прогресс и сравнение матчей) остаётся самостоятельной задачей.

- **Маршрут:** `/profile`, защищённый текущей сессией; открывается нажатием на Steam-аватар справа в шапке. Не принимать произвольный SteamID из параметров браузера как идентификатор владельца приватного профиля.
- **Идентичность:** проверенный SteamID64, исходный ник и аватар (при доступности); SteamID64 и идентификаторы OpenDota/Dota 2 не отождествлять без документированного и проверенного преобразования.
- **Источники:** OpenDota для доступных статистик игрока и матчей; Supabase/RLS для личных отчётов DotaZ. Источники независимы, ошибки и приватность не должны блокировать показ остальных доступных секций.
- **Секции:** последний и недавние матчи, общее число матчей и winrate при подтверждённой методике, самые частые герои, активность за примерно три месяца, роли/линии при наличии подтверждённых данных, сохранённые отчёты и прогресс основной Task 20.
- **Надёжность:** отсутствие/приватность данных ≠ ноль; не вычислять winrate из неполной выборки как lifetime-показатель, не выдумывать роли и не показывать чужую историю.

## 17. Task 20A — реализованная часть Steam-аутентификации (2026-11-10)

**Статус:** `in_progress`. Реализован код клиента, серверной функции и миграции; **функция не задеплоена, миграция не применена, реальный Steam-вход не проверялся.** Раздел описывает то, что реально написано, и отдельно — то, что осталось.

### 17.1 Разделение слоёв

```text
Browser (React)
  └─ LoginPage -> AuthContext.startSteamSignIn() -> window.location = {VITE_STEAM_AUTH_URL}/login?next=…
Edge Function `steam-auth` (Deno, service_role в секретах)
  ├─ /login     : state (32 байта) -> HMAC-подпись -> HttpOnly cookie -> redirect на Steam checkid_setup
  ├─ /callback  : verifySteamAssertion() -> resolveOrCreateSteamUser() | linkSteamToExistingUser() -> issueSession()
  └─ redirect   : {APP_ORIGIN}/auth/steam/callback?token_hash=…&next=…
Browser
  └─ SteamCallbackPage -> AuthContext.completeSteamSignIn() -> supabase.auth.verifyOtp({ type: 'email', token_hash })
       └─ реальная сессия Supabase, auth.uid(), существующие RLS
```

Ключевое: личность создаёт **только** серверная часть после проверки подписи у Steam. Клиент не читает SteamID из URL и не формирует сессию сам.

### 17.2 Интеграция с Supabase Auth (поддерживаемый путь)

Steam не является поддерживаемым провайдером Supabase, поэтому используется не OAuth-провайдер, а **серверный обмен проверенной личности на одноразовый email-токен**:

1. `admin.auth.admin.createUser({ email_confirm: true, app_metadata: { steam_id64 } })` — только для нового Steam-пользователя.
2. `admin.auth.admin.generateLink({ type: 'magiclink', email })` → `properties.hashed_token`.
3. Клиент вызывает **штатный** `auth.verifyOtp({ type: 'email', token_hash })` и получает настоящую сессию Supabase.

Произвольные JWT не создаются, `service_role` в браузер не попадает, `auth.uid()` и RLS работают без изменений.

### 17.3 Гарантии безопасности (реализованы и покрыты тестами)

| Требование | Реализация |
|---|---|
| Проверка утверждения | `openid.mode=id_res`, `op_endpoint` строго `https://steamcommunity.com/openid/login` |
| Подпись | обязательный POST `check_authentication`, требуется `is_valid:true`; сеть/таймаут → отказ |
| `realm` | сравнивается origin с origin `return_to` |
| `return_to` | сравнение origin + пути + полного набора параметров |
| CSRF | `state` 32 случайных байта, сверка с подписанной cookie |
| Replay | `response_nonce` не старше 5 минут + набор использованных nonce |
| Redirect | только внутренние пути; внешние адреса и `/login` отбрасываются |
| SteamID64 | строка, ровно 17 цифр, диапазон через `BigInt`, без `Number` |
| Дубликаты | `user_id` PK и `steam_id64 unique` в БД + проверки в коде |
| Изменение личности | нет политик INSERT/UPDATE/DELETE; триггер запрещает менять владельца и SteamID |
| Секреты | только `supabase secrets`, никогда `VITE_*` |
| Аватар | allowlist хостов Steam, только https, `referrerPolicy="no-referrer"` |

### 17.4 Отклонения и ограничения

- **Защита от replay — в PostgreSQL** (`public.steam_openid_nonces` + `steam_consume_nonce()`): решение принимает база через `INSERT … ON CONFLICT DO NOTHING`, поэтому защита работает между инстансами (см. §18). До применения миграции `20261110130000` RPC-функции недоступны, и вход отклоняется (fail-closed), а не обходится. В памяти инстанса осталась только **best-effort защита от перебора** (`allowRequest`, 20 запросов/мин/источник); строгие лимиты задаёт платформа.
- **Служебный email** `steam+<steamid64>@users.dotaz.invalid` создаётся только для новых Steam-пользователей; пароль не задаётся, домен `.invalid` не может принимать почту. Публичная форма email/password пока остаётся рабочей для legacy-аккаунтов.
- **Привязка** выполняется только по действующей сессии владельца (`Bearer`), UUID не меняется. Если поддерживаемый механизм когда-либо потребует нового пользователя, это будет блокером, а не поводом пересоздавать аккаунт (из-за `on delete cascade`).
- **Публичный профиль** Steam необязателен: без `STEAM_WEB_API_KEY` вход работает, ник и аватар отсутствуют, интерфейс показывает нейтральную заглушку.
- **Реальный Steam-вход не выполнялся**: тесты используют моки `fetch` и in-memory шлюз, поэтому они доказывают логику, но не факт успешной аутентификации у настоящего Steam.

### 18.2 Почему память процесса недостаточна

Edge Function масштабируется горизонтально: два запроса одного пользователя могут попасть в разные инстансы. Хранилище в памяти не разделяется, поэтому повторный `callback` с тем же `nonce` прошёл бы проверку во втором инстансе. Перенос решения в PostgreSQL устраняет эту зависимость: `INSERT ... ON CONFLICT DO NOTHING` выполняет одна транзакция под блокировкой уникального индекса, и `found` равен `true` только у одного вызова.

### 18.3 Поток с кодом обмена

```text
Steam → GET /steam-auth/callback
   verifyOpenIdAssertion()
   consumeNonce()            -- PostgreSQL, атомарно
   resolveOrCreateUser() | linkSteamToExistingUser()
   createExchange(codeHash, userId, steamId64, ttl=120s)
   Set-Cookie: dotaz_steam_bind=<HMAC(code)>
   → 302 {APP_ORIGIN}/auth/steam/callback?code=<opaque>&next=<safe path>

Browser → POST /steam-auth/exchange  { code }  (credentials: include)
   Origin === APP_ORIGIN
   cookie dotaz_steam_bind совпадает с HMAC(code)
   redeemExchange(codeHash)  -- атомарно, ровно один раз
   generateLink() → token_hash
   → 200 { token_hash }      -- токен в теле, не в URL

Browser → supabase.auth.verifyOtp({ type: 'email', token_hash })
```

### 18.4 Что даёт схема и чего не даёт

| Угроза | Закрыто | Как |
|---|---|---|
| Токен в истории браузера / `Referer` / логах | да | в URL только код; токен в теле POST |
| Повтор кода обмена | да | `UPDATE ... WHERE consumed_at IS NULL`, TTL 120 с |
| Кража кода из чужого браузера | частично | `HttpOnly`-cookie привязки + `Origin` |
| Повтор OpenID-ответа между инстансами | да | таблица nonce |
| «Сжигание» nonce поддельными ответами | да | nonce потребляется только после `is_valid:true` |
| Утечка таблицы обменов | да | хранится только SHA-256, код восстановить нельзя |
| Перебор | частично | лимитер в памяти инстанса; строгие лимиты — на платформе |

Ограничения, которые нужно понимать: `Origin` проверяется по заголовку (браузер его подделывать не может, но небраузерный клиент может); лимитер в памяти не распределённый; при отключённых cookie обмен не сработает — это осознанный fail-closed.

### 18.5 Частичные сбои

| Шаг | Поведение при сбое |
|---|---|
| `check_authentication` | вход отклонён, ничего не записано |
| `consumeNonce` (БД недоступна) | вход отклонён (`nonce_store_unavailable`) |
| `createUser` (Supabase) | попытка восстановления через `generateLink`; иначе ошибка |

| `createExchange` | вход отклонён (`exchange_failed`), сессия не выдаётся |
| `redeem` | код недействителен, токен не выдаётся |
| `generateLink` | `session_failed`, код уже израсходован (повторная попытка требует нового входа) |


## 19. Task 20A.4 — топология, PKCE и JWT функции (2026-11-10)

### 19.1 Почему cookie-привязка не работает в целевой топологии

| Свойство | Значение |
|---|---|
| Origin приложения | `https://dotaz.example` (пример) |
| Origin функции | `https://<ref>.supabase.co` |
| Отношение | **разные сайты** (разные registrable domains), не просто разные origins |
| `SameSite=Lax` | не отправляется в кросс-сайтовом `fetch`/`POST`; отправляется только при top-level GET-навигации |
| `credentials: 'include'` | включает отправку **разрешённых** cookie, но не отменяет SameSite |
| `SameSite=None` | требует `Secure` и всё равно блокируется политиками сторонних cookie |

Следствие: `dotaz_steam_bind` не дошла бы до `POST /exchange`, и вход ломался бы на последнем шаге. State-cookie при этом остаётся рабочей, потому что она ставится и читается **на одном и том же origin функции** (функция → Steam → функция).

### 19.2 Выбранная архитектура: PKCE вместо cookie (вариант C)

```text
Приложение (origin A)
  createCodeVerifier() -> sessionStorage[A]
  challenge = SHA-256(verifier)
  redirect https://.../steam-auth/login?next=...&challenge=<hex>

Функция (origin B)
  state cookie (origin B, SameSite=Lax) + challenge внутри подписанного state
  redirect на Steam checkid_setup

Steam -> Функция /callback
  проверка assertion -> nonce в PostgreSQL -> resolve/link user
  INSERT exchange(code_hash, code_challenge, user_id, ttl=120s)
  redirect origin A: /auth/steam/callback?code=<opaque>

Приложение (origin A)
  POST /steam-auth/exchange { code, verifier }   ← без cookie
  -> UPDATE ... WHERE code_hash=$1 AND code_challenge=$2 AND consumed_at IS NULL AND expires_at > now()
  -> generateLink -> { token_hash } в теле
  -> supabase.auth.verifyOtp(...)
```

Почему это эквивалентно безопасно: секрет не покидает origin приложения, на сервере хранится только его хэш, списание атомарное, TTL короткий, чужой секрет не гасит код (неудачная попытка не блокирует настоящего пользователя).

### 19.3 JWT-конфигурация функции

`supabase/config.toml`:

```toml
[functions.steam-auth]
verify_jwt = false
```

Обоснование: шлюз Supabase по умолчанию требует JWT; `/login`, `/callback` и `/exchange` вызываются без него (навигация и анонимный fetch). Отключение на шлюзе не делает эндпоинты доверенными — каждый проверяет своё:

| Эндпоинт | Что проверяется |
|---|---|
| `GET /login` | валидность `challenge`, длина `state`; ничего не принимает на веру |
| `GET /callback` | подпись Steam, `state`, `return_to`, `realm`, nonce в PostgreSQL |
| `POST /exchange` | `Origin`, формат кода и секрета, атомарное списание, TTL |
| `POST /link/start` | `Origin` + `Authorization: Bearer` + `admin.auth.getUser()` |

### 19.4 Восстановление аккаунта: правило fail-closed

`acceptRecoveredUser(app_metadata, steamId64)` возвращает `true` только при точном совпадении строкового `app_metadata.steam_id64`. Отклоняются: отсутствие метаданных, чужой SteamID, число вместо строки, некорректный ожидаемый идентификатор. Это закрывает сценарий, в котором адрес `steam+<id>@users.dotaz.invalid` заранее зарегистрирован другим способом.

### 19.5 Что не проверено

Схема проверена статически (тесты читают `?raw` исходники миграций и функции) и логически (моки). Локальной базы нет: SQL-функции не исполнялись, реальный Steam-вход и реальный обмен токена не выполнялись.

### 20.1 Проверенный контракт (по `.d.ts` установленных пакетов)

| API | Что подтверждено | Что остаётся неизвестным |

### 20.2 Следствие для восстановления аккаунта

`generateLink` — **не** «только чтение»: для `magiclink` он создаёт пользователя. Поэтому попытка восстановления разрешена исключительно при явных кодах «пользователь уже существует». Иначе любая транзиентная ошибка создавала бы аккаунт без `app_metadata.steam_id64`, который затем отвергается проверкой метаданных — то есть «мёртвый» аккаунт, занимающий служебный адрес.

### 20.3 Конфигурация домена

`STEAM_IDENTITY_EMAIL_DOMAIN` (по умолчанию `users.dotaz.invalid`) вынесен в переменные функции, потому что проект Supabase может отклонить адрес с `email_address_invalid`. Смена домена после первых входов недопустима: адреса уже используются как технические логины.

### 20.4 Граница ответственности

Всё, что можно было проверить локально, проверено: типы SDK, статические проверки миграций, логика на моках, сборка. Дальше начинается зона, требующая удалённого проекта, секретов и реального Steam — это перечислено в `README.md` (runbook и чек-лист).

**Атомарности между Supabase Auth и PostgreSQL нет.** Восстановление намеренно идемпотентно и не удаляет пользователей.
