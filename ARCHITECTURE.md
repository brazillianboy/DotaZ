# DotaZ — Architecture

**Актуализация:** 2026-11-08. Сохранены исходные технические разделы Tasks 1–15; ниже добавлены сведения по отчётам Cline о Tasks 16–18 и новый план Tasks 19–23. Task 18 ожидает ручной приёмки и commit/push. Канонический roadmap: [`PLAN.md`](PLAN.md).

## 1. Стек и архитектурные принципы
- Клиент: React 18, TypeScript, Vite, React Router, CSS, Vitest.
- Учётные записи и постоянное хранение: Supabase Auth + PostgreSQL с RLS.
- Внешние игровые данные: OpenDota API. Запросы загрузки матча и обработки реплея выполняются по фактически подтверждённому API; закрытые ключи в браузер не помещаются.
- Истина: реальные значения API и сохранённые снимки. Отсутствие поля обозначается `null`, не нулём. Наблюдения не приравниваются к оценкам без проверенных норм.
- RU/EN — перевод представления, не модификация фактов и сохранённых снимков.

## 2. Маршруты
- `/` — главная страница, ввод ID, переключение языка.
- `/matches/:matchId` — итог матча, десять игроков, выбор участника, анализ 0–15 минут, предметы, наблюдения и сохранение.
- `/history` — личные отчёты текущего аккаунта; защищён `ProtectedRoute` и RLS.
- `/login`, `/register`, `/auth/confirm` — Supabase Auth.
- `/heroes` — существующая страница, но полноценный актуальный каталог/мета пока не реализованы.
- Неизвестный маршрут — 404.

Task 15 **уже изменила только** `/matches/:matchId`; остальные маршруты не были предметом её редизайна. Новые страницы/разделы Tasks 19–20 пока не реализованы.

## 3. Путь данных матча и обработка реплея
1. Валидация числового ID, проверка состояния авторизации.
2. Поиск личного отчёта в Supabase по `(user_id, match_id)`; подробный сохранённый снимок может использоваться напрямую.
3. При отсутствии достаточных подробных данных — получение данных OpenDota `GET /api/matches/{match_id}` и проверка заполненности.
4. Если подробные поля отсутствуют и обработка доступна — автоматический запрос OpenDota на разбор реплея, ограниченный опрос статуса с backoff, повторное получение матча после успешного завершения.
5. Нормализация → анализ подтверждённых фактов → визуализация → первоначальное сохранение или контролируемое обновление улучшенного личного отчёта.
6. Если реплей недоступен/обработка не завершилась — частичный отчёт с понятным статусом; приложение не должно бесконечно отправлять запросы.

Реализованные модули Task 14: `src/lib/replayParsing.ts`, `opendotaParse.ts`, `matchParseFlow.ts`, `matchReportFlow.ts`, `matchReports.ts`, `matchReportsSupabase.ts`, `items.ts` и компоненты соответствующих панелей. Перед следующей задачей сверять реальные сигнатуры с кодом.

## 4. Нормализация и аналитика
- Данные матча: ID (строка), длительность, победитель, десять игроков с `player_slot`, `hero_id`, K/D/A, GPM, XPM, итоговые LH и прочими реально доступными полями.
- Интервал нового анализа **00:00–15:00**: `lh_t[15]`, `gold_t[15]`, `xp_t[15]`; события от 0 до 900 секунд включительно. Не заменять их полными итоговыми показателями матча.
- Необязательные данные: `kills_log`, `deaths_log`, `purchase_log`, `lane_efficiency_pct`; отсутствие даёт ограничение анализа.
- В новой аналитике правила `1.1.0`; метрики/доказательства относятся к фактическим данным. Неподтверждённых норм героя/роли нет.
- Старые сохранённые отчёты версии 1 корректно обозначают **00:00–10:00**, без переинтерпретации чисел как 15-минутных.

## 5. Правила показа предметов Task 14
**Сырые журналы не фильтруются при сохранении.** Фильтрация — только на уровне представления.

| Раздел | Показывать | Скрывать |
|---|---|---|
| Покупки 00:00–15:00 | Компоненты, готовые предметы, Bottle, Aghanim's Shard, Refresher Shard, Cheese, Block of Cheese | Обычные расходники, варды, Smoke, Dust, TP, рецепты |
| Предметы за весь матч | Значимые готовые предметы, Bottle, базовые Boots of Speed при отсутствии подтверждённого улучшения; Aghanim's Shard как значимое улучшение | Прочие сырые компоненты, обычные расходники, рецепты; Refresher Shard/Cheese/Block of Cheese не включать лишь на основании исключения ранней стадии |

- Сохранять фактический порядок и повторные события в раннем журнале; в сводке полного матча — подтверждённое время первой покупки/получения.
- При улучшении сапог в журнале скрывать базовые Boots of Speed по согласованной логике.
- Название `ultimate_scepter` показывать как **Aghanim's Scepter**; ключ API не переписывать.
- При неизвестном ключе предмета не выдумывать классификацию полноценного предмета.

## 6. Хранение и защита
- `public.profiles`: профиль владельца с привязкой к `auth.users`.
- `public.match_reports`: `id`, `user_id`, `match_id`, `status`, `match_payload`, `analysis_payload`, `rules_version`, `source`, `fetched_at`, `created_at`, `updated_at`.
- Уникальность `(user_id, match_id)`; RLS обеспечивает чтение/запись своих записей.
- Snapshot v2 добавляет `laning.interval` и `purchaseLog`; версии v1/v2 читаются. Неизвестные версии должны отвергаться безопасно.
- Усовершенствованный отчёт заменяет существующий только после валидации улучшения данных, без изменения `user_id` и `match_id`; ошибки сохранения не скрываются.
- Никогда не помещать ключ `service_role` или другой приватный секрет в Vite-клиент. `VITE_*` переменные доступны браузеру.

## 7. Локализация, состояния и ограничения
- RU/EN: словари `src/i18n`, переключатель, локализация UI/ошибок/известных правил; сохранённые отчёты не пересчитываются из-за смены языка.
- Состояния: загрузка, частичный/полный отчёт, обработка реплея, отсутствие реплея, ошибки OpenDota (404, 403, 429, 5xx), авторизация, ошибки Supabase, недоступные показатели.
- Успешная автоматическая обработка любого заданного реплея не гарантирована: требуется его доступность у провайдера.
