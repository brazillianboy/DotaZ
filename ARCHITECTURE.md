# DotaZ — архитектура MVP (редакция 2026-10-14)

## 1. Цель
DotaZ — сайт анализа матчей Dota 2 по ID матча, с понятной статистикой, обоснованными наблюдениями и историей отчётов аккаунта. Принцип: не выдавать гипотезы за доказанные игровые ошибки.

## 2. Пользовательский сценарий
1. Пользователь регистрируется и подтверждает электронную почту, затем входит в аккаунт.
2. На главной вводит числовой ID матча (положительное целое), нажимает «Анализировать».
3. Система проверяет существующий отчёт для пары `(user_id, match_id)`. Если он есть, открывает его без повторной записи.
4. Иначе серверная часть запрашивает OpenDota и нормализует полученные данные; ошибка API не превращается в «матч не найден».
5. Пользователь видит сводку матча и 10 игроков, может выбрать игрока; при достаточных данных видит отдельный анализ линии 00:00–10:00.
6. Система сохраняет один отчёт с разделами всех участников для текущего пользователя.
7. История доступна только владельцу; интерфейс поддерживает русский и английский языки.

## 3. Маршруты
- `/` — главная страница, описание функций, ввод ID, переключение языка.
- `/heroes` — герои и статистика (при наличии подтверждённого источника и периода обновления).
- `/matches/:matchId` — сводка матча, десять игроков и подробный отчёт выбранного участника; выбранный игрок — состояние страницы, не отдельная запись истории.
- `/history` — отчёты только текущего аккаунта.
- `/login` — вход; `/register` — регистрация; `/auth/confirm` — обработка подтверждения (маршруты рекомендованы, не подтверждены исходным кодом).

Для защищённых страниц требуется активная сессия. После входа пользователь возвращается к запрошенной странице.

## 4. Компоненты
`AppHeader`, `LanguageSwitcher`, `MatchIdForm`, `MatchSummary`, `PlayerSelector`, `PlayerStats`, `LanеReport`, `EvidenceList`, `RecommendationsList`, `ReportLimitations`, `LoadingState`, `ErrorState`, `HistoryList`, `HeroStats`.

UI-состояния: `idle`, `loading`, `ready`, `partial`, `not_found`, `invalid_id`, `rate_limited`, `upstream_error`, `unauthorized`. Показывать конкретные причины и кнопку ручного повтора для временных ошибок; не обещать успешный анализ, когда API недоступен.

## 5. Источник данных и доверие
**Подтверждено в исходных материалах:** OpenDota `GET /api/matches/{match_id}`; базовые поля `match_id`, `duration`, `radiant_win`, `players`, `player_slot`, `hero_id`, `kills`, `deaths`, `assists`, `gold_per_min`, `xp_per_min`, `last_hits`. Для тестового матча `9007760151` после обработки реплея ранее были получены `lh_t`, `gold_t`, `xp_t`, `kills_log`, `deaths_log`, `purchase_log`, `lane_efficiency_pct`. Это результат ранее проведённой проверки, а не гарантия наличия полей для каждого матча.

**Подтверждено в исходных материалах:** OpenDota Benchmarks с `hero_id` и `role` предоставляет сравнительные показатели целого матча и различает `core`/`support`. Эти процентили **нельзя** применять как нормы первых десяти минут.

Нормализация: отсутствующие поля обозначаются `null` (не `0`), все вычисляемые выводы содержат ссылку на исходный показатель и метод. Кэширование результатов внешнего API допустимо; источник и время получения сохраняются.

## 6. Правила аналитики
### 6.1 Итоговые показатели матча
Отображать K/D/A, KDA (формула должна быть единой для интерфейса и тестов), GPM, XPM, добивания, урон по героям/постройкам, предметы и другие фактически доступные значения. Указывать, когда показатель отсутствует. Не путать `last_hits` с числом всех убитых крипов; не называть суммарное золото полученным, если соответствующее поле не было получено.

### 6.2 Стадия линии: 00:00–10:00
Показывать фактические добивания к десятой минуте, золото, опыт, убийства, смерти и покупки за период **только если соответствующие временные ряды/логи доступны**. Не вычислять показатели линии из итоговых GPM/XPM матча. Для покупки указывать время события, но **не** маркировать её как «раннюю/позднюю» без проверенной нормы для героя, роли и контекста.

Оценку «хорошо/плохо», сравнение с ролью/героем, ранжирование ошибок и уверенность в выводе включать **только после** определения методики роли, источника репрезентативных норм за 10 минут и тестов на эталонных матчах. До того используется метка **«наблюдение, не оценка»**.

### 6.3 Правила рекомендаций
Каждая рекомендация должна иметь `rule_id`, `rule_version`, `player_slot`, `evidence` (поля, значения, интервал), `limitations` и текст. При недостатке данных блок оценки заменяется сообщением «Недостаточно данных для достоверной оценки».

## 7. Путь данных
`MatchIdForm` → валидация ID → проверка сессии → запрос отчёта пользователя `(user_id, match_id)` → при отсутствии серверный вызов OpenDota → нормализация → вычисление достоверных наблюдений → сохранение отчёта → визуализация.

На клиенте не хранить `service_role` и секреты OpenDota. Доступ к таблицам истории через Supabase Auth и RLS. Внешние запросы с секретами выполнять на доверенном сервере или Edge Function. Даже если пользователь меняет `user_id` в запросе, сервер должен использовать `auth.uid()`.

Повторный запрос того же матча должен возвращать существующий отчёт. При конкурентных запросах уникальный индекс `(user_id, match_id)` предотвращает дубли; обработка конфликта возвращает существующую запись. Если один процесс ещё вычисляет отчёт, показывать его статус, а не перезаписывать неопределёнными данными.

## 8. Постоянное хранение
Supabase PostgreSQL — единое постоянное хранилище. Рекомендуемые сущности:
- `profiles`: `id` (совпадает с `auth.users.id`), `nickname`, `created_at`.
- `match_reports`: `id`, `user_id`, `match_id`, `status`, `match_payload` (сводка и данные всех десяти игроков), `analysis_payload` (наблюдения, рекомендации, ограничения), `rules_version`, `source`, `fetched_at`, `created_at`, `updated_at`.
- Ограничение `UNIQUE (user_id, match_id)`.
- RLS: чтение, создание, изменение, удаление — только владелец; `user_id` берётся из текущей сессии. SQL-миграция находится в `supabase/migrations/20261014_dotaz_initial.sql`.

Это **проектная схема**, её применение к существующей БД без просмотра миграций и данных не разрешено.

## 9. Отказы и ограничения
- Некорректный ID → подсказка исправить ввод.
- Реальный 404 от провайдера → «Матч не найден».
- 401/403 внешнего API → конфигурация/доступ провайдера, **не** «матч не найден».
- 429 → «Лимит запросов, повторите позже».
- 5xx/таймаут/сеть → временная ошибка и возможность повтора.
- Матч без расширенных данных → частичный отчёт с фактическими показателями и явными ограничениями.
- Ошибка авторизации → предложить войти; доступ к чужой истории запрещён.

## 10. Объём MVP и отложенные функции
MVP: регистрация, вход, ввод ID, статистика матча и игроков, достоверные наблюдения, частичный отчёт, история одного отчёта на матч и пользователя, русский/английский интерфейс.

Отложено до проверки источников/правил: доказательные оценки качества линии, актуальная мета (источник, окно выборки, патч), сравнение героя и роли по линии, загрузка реплея пользователем, монетизация и реклама.

## 12. Контрольные тесты
1. Невалидный ID не запускает внешний запрос.
2. Для существующего матча доступны 10 игроков; отсутствующие поля отображаются как недоступные.
3. Повторные и параллельные запросы одного матча одним пользователем не создают вторую запись.
4. Разные пользователи могут иметь собственный отчёт одного матча и не видят чужую историю.
5. Нет временных логов → нет оценочных суждений о линии.
6. Benchmarks целого матча не используются как нормы `00:00–10:00`.
7. API отвечает 403/429/500 → UI показывает корректный тип ошибки, без ложного «матч не найден».
8. Невалидная/истёкшая сессия блокирует доступ к истории.
